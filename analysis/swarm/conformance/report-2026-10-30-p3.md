## Design observations (not task failures)

1. **Trajectory timing.** The recorder writes one file at the end of `run_fix`. A crash (provider error, `TimeoutExpired` from a gate) loses every step. The explainer (edge 10) says "trajectory (append per step)".
2. **Budget accounting.** `used` is the cumulative sum of tokens in, out and cached over all steps (plus the observation's character count), not the current window size. Strategies would fire too early on long runs. The explainer says "at 80% of the window".
3. **Caps are conditional.** The 8000-character cap only runs when `context_budget` and `strategy` are passed. `run_baseline` passes neither, so a 5 MB read reaches the model in the baseline. The phase's fix text says a single result must not exceed a share of the window at the dispatch boundary.
4. **Replay.** `fix-loop replay` edits the current directory (run in a checkout, it changes your files). It sees only the `{"tool","arguments"}` message text; a provider `tool_calls` reply is stored as `completion.content`, so it would be invisible. Edits made through the shell are not reproduced (as the AC allows).
5. **`failed` is overloaded.** Three consecutive tool results with code `failed` (for instance non-UTF-8 files) count as `retry-cap` the same as malformed arguments.
6. **Explainer vs code.** `hld-edges` S3 stops list six codes; the code has eight (`retry-cap`, `summary` added). EC-49 says head+tail truncation; the cap is head-only (the code says so). `d2s-mcp` is not called anywhere in the loop.
