## Cross-cutting checks

**Gates and ordering (ADR-012).** The order, the short-circuit and the soft-failure rule are implemented as the ADR says. Axe reports only rule ids new versus a baseline; console reports only new errors and warnings versus a baseline (both exact-text/id match). The judge is not in `ORDER`.

**Pixel check problems (T02, T26).**
- *Not usable at real size.* The fringe test compares every changed pixel with every unchanged pixel. A 300x150 image with about 3% changed took **46 s**; 200x100 took 1.1 s; 100x50 took 0.06 s. A 1280x720 screenshot would take hours.
- *Thin changes pass.* A changed pixel within 1 px of an unchanged one counts as fringe, and up to 10% fringe passes. A full-width 1 px hairline passes (probe: `ok=True`). Thin glyph strokes or hairline borders can change without failing, so the check can accept a real thin-stroke regression. The 4 px shift correctly fails.
- The CI fixtures are tiny (72-byte PNGs), which hides both problems.

**Alpha (T12, ADR-013).** The nominal two-coder formula is correct (0.692 reproduced). Edge cases: two coders who both use one label give alpha 1.0 (the standard value is undefined); the bootstrap sorts samples that can be NaN; the upper percentile index is off by one. The bootstrap interval is seeded and works (a probe returned (0.48, -0.04, 0.805)). An unparsed judge string stays in the denominator as `error`, tested.

**Judge (ADR-013).** Advisory only is written and consistent: `fail` does not reject a patch whose checks passed; a flagged injection or an error does not accept one. No number is cited from an unlabelled run (the only numbers are the published alpha example and a Wilson unit test). The Verdict does **not** carry a judge label (`Verdict` is `ok`, `checks`, `first_failure`, `failed_check`), so the judge is not part of the verifier's output.

**Best-of-k (ADR-014).** `best_of_k(k, ...)` takes `k` as a required argument with **no default**, rejects only `k < 1`, and has **no cap**: `best_of_k(6, ...)` runs. The "ledger" is a local `UsageLedger` list, not `argus_core.ledger`, so it enforces no quota. It draws and verifies all k candidates even when the first passes. The ADR text and the README claim a default of 1 and a cap of 5 that the code does not implement. The default-and-cap claim is exactly what the task asked me to check.

**Wiring into fix-loop (T22).** The hook is correct and tested, and fails closed. It does not break P3: all 51 fix-loop tests pass. But nothing constructs the `verify` callable (no code runs `verify.pipeline.run` against captured screenshots, and `run_baseline` passes none), so by default no run is verified. The verifier is wired in as an optional callback only.
