## 2. TLS

**What DBOS does with the URL's `sslmode`.** `dbos/_sys_db_postgres.py` makes the engine with `sa.make_url(url).set(drivername="postgresql+psycopg")`. SQLAlchemy's psycopg dialect hands the URL's query string (`sslmode`, `channel_binding`, `sslrootcert`, ...) to `psycopg.connect` as libpq options. DBOS adds none and removes none. Shown with the same two calls on the local server: `sa.create_engine(sa.make_url(url).set(drivername="postgresql+psycopg"))` with `sslmode=require` connected with `pg_stat_ssl.ssl = true`; the same URL with `sslmode=disable` connected with `false`.

**Seen.** A local Postgres 16 with `ssl=on` and a self-signed certificate, URL ending `?sslmode=require`. After `launch()`, `pg_stat_ssl` joined to `pg_stat_activity` showed every DBOS connection (`application_name = dbos_transact`) with `ssl = true`, protocol `TLSv1.3`: 5 of 5 in a probe, 4 of 4 in the test `test_dbos_talks_to_the_database_over_tls`.

**Guard in code.** libpq's default `sslmode=prefer` quietly uses plain text if TLS fails. `FlowSettings.from_env` therefore refuses a URL whose host is not `localhost`, `127.0.0.1`, `::1` or a Unix socket unless `sslmode` is `require`, `verify-ca` or `verify-full` (`require_tls`; tests in `test_config.py`). The error text names only the variable, never the URL.

**`require` is not authentication.** `sslmode=require` encrypts but does not check the server's certificate. `sslmode=verify-full&sslrootcert=system` does, with the operating system's roots (libpq 16 and newer; the bundled libpq here is 18.4). It is accepted by `require_tls` but was **not** tried: the local certificate is self-signed, and no Neon endpoint was reachable. Start with `sslmode=require` as Neon's own connection string has it; move to `verify-full` after trying it once on Render (a failed certificate check shows in the logs as a connection error).

**Logging.** The password is never logged by our code (tests assert it). DBOS itself logs the URL at INFO level at start-up with the password masked (`postgresql://user:***@host/db?sslmode=require`): the user name, host and database are visible in the Render log. DBOS's connection-error warnings print the driver's message; in the runs below they did not contain the URL or password. `grep` for the generated password in the whole pytest output found 0 matches.

## 3. Which Neon endpoint: direct, not pooled

Neon gives each branch two host names: a direct one (`ep-<name>-<id>.<region>.aws.neon.tech`) and a pooled one (same with `-pooler` after the endpoint id), the latter going through PgBouncer in transaction mode (my knowledge of Neon, not checked against the live docs today).

Use **direct** for `ARGUS_FLOW_DATABASE_URL`:

- `use_listen_notify` is off, so the pooled endpoint's lack of `LISTEN` is not the reason. The reasons are what else DBOS does on its connections, read from the 3.4.0 source: the migration takes a session-level advisory lock (`pg_try_advisory_lock`, then `pg_advisory_unlock` on the same connection), and every new connection runs a session-level `SET idle_in_transaction_session_timeout`. Both assume that one client keeps one server connection. DBOS has been written with transaction pooling in mind elsewhere (per-statement `SET LOCAL`, transaction-level advisory locks for its background jobs), so the pooled endpoint may well work; I could not test it, and the direct endpoint costs nothing here.
- One Render instance, one DBOS pool (20 connections by default, `pool_pre_ping` on). That fits a direct endpoint. What Neon's free compute allows as `max_connections` is **not** in the T00 notes and I did not look it up. If the owner sees "too many connections", set a smaller pool: add `sys_db_pool_size` to `dbos_config` (not done, no evidence it is needed).
- Polling vs scale to zero is T14's measurement; nothing here keeps the database awake on purpose.

## 5. Reconnect after the database suspends

**What dbos 3.4.0 already does** (read from the installed package; the line numbers are for 3.4.0):

| Where | Behaviour |
|---|---|
| `_dbos_config.py` `configure_db_engine_parameters` | system-database engine has `pool_pre_ping=True`, `pool_size=20`, `pool_timeout=30`, and `connect_timeout=10` unless the config sets one |
| `_sys_db.py` `db_retry` | wraps nearly every system-database operation (enqueue, step result, `recv`, workflow status). A connection error (`connection_invalidated`, "connection failed", "server closed the connection unexpectedly", connection timeout, SQLSTATE class 08, 53, 57) is retried with exponential backoff, 1 s doubling to 60 s, jittered, and **no deadline**; the call blocks. It can be turned off only through the DBOS client's `retry_connection_errors`, which `DBOSConfig` does not expose |
| `_sys_db_postgres.py` `run_migrations`, called from `DBOS.launch()` | **no retry**: one connect with a 10 s timeout, then the SQLAlchemy error |

Measured in a probe on this machine (Docker Desktop, Windows): `launch()` with the server stopped raised `sqlalchemy.exc.OperationalError ... ConnectionTimeout: connection timeout expired` after 20.1 s. With every DBOS connection killed by `pg_terminate_backend`, the next `enqueue` took 0.17 s and ran: `pool_pre_ping` replaced the dead connections before any query failed.

**What T11 added, in the smallest place:** [`flow/db_wake.py`](../../packages/flow/src/flow/db_wake.py), `wait_for_database(url)`: connect, `select 1`; on a connection error wait 1, 2, 4, 8, 15 s, at most 6 attempts, 5 s connect timeout per attempt (so about 60 s at most; the numbers are module constants, a guess to be confirmed by T13/T14, not a measurement). It logs `database not ready, attempt N of 6 (OperationalError); retrying in X s` with the exception class only, and raises `DatabaseUnavailable` without the URL. Used in two places:

- `launch()`, before `DBOS(...)`, so a cold or restarting database delays the start instead of killing it.
- `DbosEnqueuer.enqueue()`, before the DBOS call, so a database that stays down gives the webhook a `DatabaseUnavailable` after about a minute (the webhook then forgets the delivery id and the poller repairs the miss) instead of a background thread blocked inside DBOS's endless retry.

Step DB access (step results, `recv`, status) needed nothing: DBOS's own retry covers it, shown in the T24 write-up ([p6-t24-break-it.md](p6-t24-break-it.md)).

Tests that need the container read `ARGUS_FLOW_TEST_CONTAINER` and refuse any name not starting with `argus-p6-pg-` (`suspend_support.py`). Without the variables they are skipped with a reason.

### Run it

```bash
# 1. a throwaway Postgres with TLS (self-signed cert made on the host, copied in; password only in an env var)
openssl req -new -x509 -days 2 -nodes -subj /CN=localhost -out /tmp/tls/server.crt -keyout /tmp/tls/server.key
PW=$(python -c "import secrets;print(secrets.token_urlsafe(18))")
docker create --name argus-p6-pg-w3d -e POSTGRES_PASSWORD="$PW" -e POSTGRES_DB=argus_flow_t11 -p 127.0.0.1:55436:5432 \
  --entrypoint sh postgres:16-alpine -c 'set -e; D=/var/lib/postgresql/tls; mkdir -p $D; cp /tmp/tls/server.* $D/; chown postgres:postgres $D/server.*; chmod 600 $D/server.key; exec docker-entrypoint.sh postgres -c ssl=on -c ssl_cert_file=$D/server.crt -c ssl_key_file=$D/server.key'
docker cp /tmp/tls argus-p6-pg-w3d:/tmp/tls && docker start argus-p6-pg-w3d
# 2. the tests
export ARGUS_FLOW_DATABASE_URL="postgresql://postgres:$PW@127.0.0.1:55436/argus_flow_t11?sslmode=require"
export ARGUS_FLOW_TEST_CONTAINER=argus-p6-pg-w3d
uv run --all-packages python -m pytest packages/flow/tests -q
# 3. remove it (also its volume)
docker rm -f -v argus-p6-pg-w3d
```

The `alpine` image has no `openssl` command, hence the certificate is made on the host. Git Bash on Windows: `export MSYS_NO_PATHCONV=1` before the `docker` lines.

## 6. What could NOT be verified without Neon

- A real suspend and wake: Neon's 5-minute idle timer, its wake-up time ("a few hundred milliseconds" per the docs; not measured), and what the first connection sees (a slow answer, a refused connection, a dropped TLS handshake). My stand-ins are `pg_terminate_backend` and stopping the container; a stopped container refuses or times out, which is not the same as a compute that answers after a delay. The 5 s per-attempt timeout is therefore a guess.
- TLS against Neon's certificate chain (`sslmode=require` is shown against a self-signed local cert; `verify-full` not tried anywhere).
- The pooled endpoint with DBOS (section 3), the free plan's `max_connections`, and whether DBOS's connect-time check for the database `postgres` (`run_migrations`, then "Could not connect ... Continuing...") is allowed for the `neondb_owner` role; DBOS continues if it is not.
- Whether DBOS's polling keeps the compute awake (T14).
- The Render side: environment variables set, Render log lines of section 4.
