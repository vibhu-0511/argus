### How the runner finds, starts and waits (`run(ticket_id, run_key, upstream)`)

1. List the runs of `agent-job.yml` (`event=workflow_dispatch`, newest 100) and look for `display_title == run_key`. The workflow sets `run-name: ${{ inputs.run_key }}`, so the run title is the key.
2. Found: skip to 4. Not found: `POST .../dispatches` with inputs `ticket_id`, `step`, `run_key`, `upstream`, then poll the list (every 2 s, up to 60 s) until the run appears. The dispatch call returns no run id.
3. Never listed within 60 s: raise `ActionsError`; the DBOS step retries, and its first act is the find, so a late-appearing run is found, not dispatched again.
4. Poll the run every 10 s until `completed`, up to 40 min (the job itself has `timeout-minutes: 30`). Timeout: `Outcome(False, ...)`.
5. List the run's artifacts, download `argus-result` (GitHub answers 302 to blob storage; httpx drops the `Authorization` header on that hop), read `result.json`, `patch.diff`, `trajectory.jsonl`.
6. `Outcome(ok, output)` with `ok = conclusion == "success" and result.json.ok`. The patch and trajectory are kept in `runner.artifacts[run_key]`.

Failures that a retry can fix (HTTP error, run not listed) raise; failures that it cannot (run concluded failure/cancelled/timed out, artifact missing or malformed, upstream over 50,000 characters) return `Outcome(False, reason)`.

### Artifact contract (what the job must upload)

One artifact named `argus-result`, files at the zip root:

| File | Required | Content |
|---|---|---|
| `result.json` | yes | `{"ok": true\|false, "output": "<text>"}`. `output` is the repro script (repro), the patch (fix) or the verdict text (verify): what the next step takes as `upstream` |
| `patch.diff` | no | the patch, for humans and for T19/T13 measurements |
| `trajectory.jsonl` | no | the step's trajectory in the `argus_core` Trajectory JSONL form |

The job writes a failure `result.json` itself if the step wrote none (`if: always()`), so a crashed step still comes back as a readable `Outcome(False, ...)`.

## NOT built: the job's entry point

`agent-job.yml` runs `uv run --package flow python -m flow.agent_job`. **That module does not exist.** `repro_agent`, `fix_loop` and `verify` expose library functions (`run_repro`, `run_fix`, `verify.pipeline.run`) that need a `Ticket`, a task directory, a model router, a worktree and the sandbox; none has a per-ticket command line. Turning an issue into those arguments (ticket adapter, which repo and commit the agent works on, model choice) is not specified in `phases/P06-argus-flow.md`, so it was not guessed. Until `flow.agent_job` exists, a dispatched run starts, fails at that step, uploads the failure `result.json`, and the runner returns `Outcome(False, "run concluded failure: the step ended before it wrote a result ...")`. That is a useful first end-to-end check of everything else (dispatch, find, wait, artifact download), but it is not the acceptance run.

The entry point contract (written into the workflow as a comment): read env `ARGUS_STEP`, `ARGUS_TICKET_ID`, `ARGUS_RUN_KEY` and the file `$ARGUS_OUT/upstream.txt`; run the step; write `result.json`, `patch.diff` and `trajectory.jsonl` into `$ARGUS_OUT`. The model key arrives as env `ARGUS_MODEL_API_KEY`.

Also unchecked on a real runner: the install steps (copied from `repro.yml`: uv, pnpm, Node 24, Playwright Chromium) and that `actions/upload-artifact@v4` puts the three files at the zip root (it uses their common folder as root, which is `argus-out`; if a real run shows a prefix, change `parse_artifact` or the `path:` list).

## Owner steps

### 1. Make the dispatch token (fine-grained, one repository)

GitHub > Settings > Developer settings > Personal access tokens > Fine-grained tokens > Generate new token.

- Resource owner: the owner of the Argus repository. Repository access: **Only select repositories** > the Argus repository.
- Repository permissions: **Actions: Read and write** (dispatch needs write; listing runs and artifacts needs read). Leave everything else at "No access" (Metadata read is added automatically).
- Expiration: 30 days, then rotate.

Do not paste the token into a file, the repo, a chat or a log. This task was built without it.

### 2. Store it

- Local smoke test: set it in your shell only, typed by you. In bash: `read -rs GITHUB_DISPATCH_TOKEN && export GITHUB_DISPATCH_TOKEN`. In PowerShell: `$env:GITHUB_DISPATCH_TOKEN = (Read-Host -MaskInput)` (PowerShell 7) .
- Deployed service (T12): Render dashboard > the service > Environment > add `GITHUB_DISPATCH_TOKEN`.
- The model key for the job is a **GitHub Actions secret**, not a dispatch-token matter: repository Settings > Secrets and variables > Actions > New repository secret `ARGUS_MODEL_API_KEY`, or `gh secret set ARGUS_MODEL_API_KEY` (it prompts; type the value there).

### 3. Enable the workflow

1. Settings > Actions > General: Actions allowed for the repository.
2. Get `.github/workflows/agent-job.yml` onto the default branch (GitHub lists a `workflow_dispatch` workflow only from the default branch; a dispatch can then name another `ref` that also has the file). That needs a push and merge, which this session did not do.
3. Actions tab > `agent-job` should show "Run workflow". If it does not, the file is not on the default branch.

### 4. Run a real dispatch by hand

```bash
gh workflow run agent-job.yml -f ticket_id='OWNER/REPO#1' -f step=repro -f run_key='argus:OWNER/REPO#1:dispatch-repro:1' -f upstream=''

gh run download <run-id> -n argus-result -D /tmp/argus-result && ls /tmp/argus-result
```

Expected once `flow.agent_job` exists: `result.json`, `patch.diff`, `trajectory.jsonl`. Until then: `result.json` with `"ok": false`.

Run it twice. The second run must print the same outcome and `gh run list` must still show one run for the key.

## Known limits (also `ponytail:` comments in the code)

- Upstream (repro script, patch) travels inline as a dispatch input; GitHub caps the payload at 65,535 characters, the runner refuses above 50,000. An artifact reference needs the earlier run's id, which the `Runner` interface does not carry.
- Only the newest 100 runs of the workflow are listed when looking for a key.
- A dispatch whose run is not listed within 60 s and is then retried could start a second run if GitHub is slower than that; the concurrency group on the key queues it behind the first instead of running both at once, but it still runs. The window is small and unmeasured.
- Polling every 10 s costs 6 API calls per minute (about 360 per hour) per waiting run against the 5,000 per hour limit.
- `workflow.py`'s step retry is 3 attempts 0.5 s then 1 s apart (a T03 comment says to tune it with the real client). With real GitHub secondary rate limits that is probably too short; not tuned, nothing measured.
- `.github/workflows/check_no_secrets.py` (an unreferenced script) now exempts `agent-job.yml` from the `secrets.` and `ARGUS_MODEL_API_KEY` markers. It still fails on `dashboard.yml`, `eval-gate.yml` and `golden.yml`; that was already so before this task and is untouched.

- The default steps are wired from the code and unrun. `verify` uses the bench scorer, not `verify.pipeline.run` (that needs screenshots and DOM reports nothing makes for a ticket).

### What the workflow does now, per step input

| Step input | What the job builds before `flow.agent_job` runs | Why |
|---|---|---|
| all three | checkout of `dcortex-ai/dcortex-platform` into `platform/` with `ARGUS_PLATFORM_TOKEN`, `persist-credentials: false`; `ARGUS_PLATFORM_REPO` = that folder | every default step reads the checkout (`git show HEAD:<css>`, `git worktree add`) |
| `repro` | `pnpm install --frozen-lockfile` in `platform/`; `docker build` of `argus-repro:p1` (`packages/repro-agent/docker`); the rig (below) | Canvas is served by Vite from the platform checkout; the repro script runs in the image on an internal Docker network |
| `fix` | `docker build` of `argus-fix-sandbox:p3` (`packages/fix-loop/docker`, an Alpine image pinned by digest) | `run_cmd` runs `sh -c` in it with no network; no node and no rig are needed |
| `verify` | nothing more | the bench scorer renders the patched CSS with the Chromium the job already installs; no Docker |

The rig on Linux. `repro_agent.trees.up()` is written for Docker Desktop on Windows: its proxy container forwards to `host.docker.internal`, and Vite listens on `127.0.0.1` only. On a Linux Docker engine neither works as is (the name is not defined, and a loopback-only listener cannot be reached from a container). Without changing the Python (it is the code the P5 runs use), the workflow does the Linux part itself, in this order:

1. read the network, proxy and alias names, the port and the proxy script from `repro_agent.trees` (so the workflow cannot drift from the code);
2. start a small relay on the host (`node -e`): it listens on the `docker0` gateway address, port 5297, and forwards to Vite on `127.0.0.1`;
3. create the internal network and the proxy container, with `--add-host host.docker.internal:host-gateway`, and join the proxy to the network under the alias `argus-app`;
4. run `python -m repro_agent.trees up`, which sees the proxy already running and only starts Vite;
5. fetch `http://argus-app:5297/` once from a container on the internal network, so a broken rig fails here, before any model call is spent;
6. at the end (always): print the last 40 lines of the Vite log, run `trees down`, stop the relay.

Also changed: the job `env` has `ARGUS_PLATFORM_REPO`. An optional repository **variable** `ARGUS_PLATFORM_REF` pins the platform commit (empty means the default branch). The seeded `bug.patch` files apply to "platform HEAD" and nothing in this repository records which commit that was, so if the default branch moved since the tasks were seeded a patch may not apply; pin the commit your local checkout was at (`git -C <platform checkout> rev-parse HEAD`). `permissions` is still `contents: read`. `ARGUS_PLATFORM_TOKEN` is read only by the checkout step's `token:`; the step that runs the model has only `ARGUS_MODEL_API_KEY`. The contract test now asserts both facts.

### `check_no_secrets.py`: no change needed

The script exempts `agent-job.yml` from the markers `secrets.` and `ARGUS_MODEL_API_KEY`. `ARGUS_PLATFORM_TOKEN` matches no marker and the existing exemption for the `secrets.` marker already covers the second reference, so the allow-list gained nothing. The allowance is not tied to a name: any new secret reference in `agent-job.yml` would also pass the script. The workflow's contract test is what pins the file to exactly two (model key, platform token). The script still fails on `golden.yml`; this task did not touch that file.

### Can the rig run on a GitHub-hosted runner?

Probably, but it has not been seen. Three things are unproven, and the first `repro` dispatch is where they get proven (step 5 above fails early and says so):

- the `docker0` relay path: that the proxy container reaches the host gateway address and that the runner's firewall lets it through;
- that a background process (Vite, the relay) started in one step is still alive in the next (it normally is on a hosted runner);
- the images' size and build time (owner steps 4 and 5).

If the relay path does not work, the smallest fix is in the code, not the workflow: add `--add-host host.docker.internal:host-gateway` to the proxy's `docker run` in `trees.py` and let `vite.config.mjs` listen on an address from an env var instead of `127.0.0.1` (about three lines). I did not do it here because `trees.py` is what the P5 runs use on your machine. An alternative I would not take: dropping the internal network on the runner. It would let a model-written script reach the internet, which is the property the sandbox exists to prevent. A self-hosted runner on your own machine would keep the rig as it is, but it runs repository workflow code on that machine; also not recommended.
