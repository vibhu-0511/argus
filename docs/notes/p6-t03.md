# P6-T03 DBOS workflow on a local Postgres

Date: 2026-11-01. dbos 3.4.0 (pinned `dbos==3.4.0` in `packages/flow/pyproject.toml`; `psycopg` 3.3.6 comes with it). Architecture: [docs/architecture/p6.md](../architecture/p6.md), section P6-T03.

## The open question from T01: does `SetWorkflowID` apply when enqueuing?

**Yes, in 3.4.0.** Tested with the real library against Postgres 16 (probe, then `test_starting_the_workflow_twice_repeats_no_side_effect`):

| Call | Result |
|---|---|
| `with SetWorkflowID(t): queue.enqueue(wf, t)` | workflow row with id `t`, status `ENQUEUED`, then `SUCCESS` |
| the same again, while the first is running or done | returns a handle with the same workflow id; no second row; the step ran once |
| the same again after the first finished | same: the finished run is returned, nothing starts (default reuse policy `return-existing`) |
| ticket ids like `owner/repo#12` | accepted as workflow ids (DBOS only rejects empty or whitespace-only ids) |

So the contract in `flow/enqueue.py` holds: workflow id = ticket id, shared by webhook and poller. One consequence, kept on purpose: once a ticket's workflow has finished, a later hint for it starts nothing. A deliberate re-run needs a new attempt (T02 reserves `attempt` in the keys) and a decision on the workflow id for it; not built here.

API facts that differ from older DBOS versions, found by reading the installed 3.4.0 source:
- A queue is made with `DBOS.register_queue(name, ...)` after `DBOS.launch()`; `Queue(...)` cannot be constructed directly. The queue config is stored in the system database.
- `DBOSMaxStepRetriesExceeded` is not exported by `dbos/__init__`; it is imported from `dbos._error`.
- `DBOS.reset_system_database()` is destructive. The tests never call it: each test uses a fresh ticket id instead.
- T00 left "default `executor_id` when unset" open: DBOS sets `GlobalParams.executor_id = os.environ.get("DBOS__VMID") or "local"` (`dbos/_dbos.py`). We set it explicitly anyway.

## Config decisions (module `flow/config.py`)

| Setting | Value | Why |
|---|---|---|
| `use_listen_notify` | `False` | Fixed when the system database is created. Polling works through any Postgres endpoint (Neon's pooled endpoint is pgbouncer, which does not carry LISTEN), and there is no long-lived LISTEN connection to go stale when Neon suspends. Cost: up to 1 s of latency on `recv` and events, irrelevant for a QA wait. Whether polling keeps Neon awake is T14's measurement. To change it later, reset the system database. |
| `application_version` | `"argus-flow-1"` | DBOS recovers only workflows of the current version and defaults to a hash of the source. Pinned, a redeploy with new code still recovers old pending workflows. Bump by hand only when old histories cannot replay (steps reordered or renamed). |
| `executor_id` | `"argus-flow-0"` | A restarted process recovers only its own executor's workflows. One executor on Render, so a fixed id lets the new instance claim the old one's work. |
| conductor | none | `dbos_config` never sets `conductor_key` or `conductor_url`; a test asserts it. |
| database URL | env `ARGUS_FLOW_DATABASE_URL` | Never printed (`FlowSettings.__repr__` hides it), never in a file. |

T11 adds on top: TLS, reconnect after suspend, the Neon endpoint choice, and a test of LISTEN/NOTIFY versus polling there.

## What T03 built and did not build

Built: `flow/workflow.py` (workflow, five steps, the injected `Runner` and `GitHubClient`, `find_or_create_pr`), `flow/dbos_runtime.py` (`DbosEnqueuer`, `launch`, `shutdown`), `flow/config.py`, `flow/fakes.py`, tests.

Not built, by design: Actions dispatch (T04), the QA signal wait (T08), the poller (T07), the crash-recovery kills (T19). The seam to T08 is one marked block in `ticket_workflow`: a stub that approves at once so a fixture run reaches `done`. Because it is a stub, `finish_step` posts the comment and label for `done` but does not mark the PR ready for review; `ready-pr` and `close-pr` (in `states.EFFECTS`) are T08's, so a PR stays draft until a real QA approval exists.

## Run it

Start a throwaway Postgres (pick any free port; keep the password out of files), run the tests, remove the container:

```bash
PW=$(python -c "import secrets;print(secrets.token_urlsafe(18))")
docker run -d --name argus-p6-pg -e POSTGRES_PASSWORD="$PW" -e POSTGRES_DB=argus_flow_test -p 127.0.0.1:55432:5432 postgres:16-alpine
export ARGUS_FLOW_DATABASE_URL="postgresql://postgres:$PW@127.0.0.1:55432/argus_flow_test"
uv run python -m pytest packages/flow/tests -q
docker rm -f argus-p6-pg
```

Without `ARGUS_FLOW_DATABASE_URL` the eight tests in `test_workflow.py` are skipped with the reason `ARGUS_FLOW_DATABASE_URL is not set; needs a real Postgres`. On Windows use `python -m pytest`; the `pytest.exe` launcher is blocked by policy on the owner's machine.

The first run applies about 125 DBOS migrations (a few seconds) and each run waits on the queue's 1 s polling, so `test_workflow.py` takes about a minute and the whole package about a minute and a half.
