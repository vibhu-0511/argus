How a run works. The guest gets 1 vCPU, 512 MiB (the fix-loop sandbox limits) and **no network device**. The init script is written into the guest rootfs as `/fixture-init`; the kernel boots with `init=/fixture-init` added to the quickstart's boot args; the script mounts a second, read-only drive on `/checks` (holds `keep.txt` = `same`), runs **the same `FIXTURE` string as `guard sandbox-run`** between two marker lines, prints `work-out=...` (the file the fixture wrote in `/work`), and powers off. Firecracker's stdout is the serial console; `guard firecracker-run` judges the lines between the markers. It needs `fixture-ok`, `checks-keep=same`, `checks-ro=yes` and `work-out=fixture-ok`. The result JSON also keeps the command, the config, the Firecracker version and the console tail. The `kernel=` line in the output shows the guest kernel.

## What T00 found about KVM

- Standard GitHub-hosted runners: **not confirmed**. No source read says `/dev/kvm` exists on `ubuntu-24.04` or `ubuntu-26.04` x64. The sentence in `PROJECT.md` that Linux runners have had it since October 2025 was found in no source and was removed.
- GitHub says: nested virtualization "is not officially supported" and any use is experimental. Only hardware acceleration for Android emulators is documented (2-vCPU Linux runners, April 2024; the workflow had to add a udev rule for the KVM group).
- Arm: one user report says `ubuntu-24.04-arm` has `/dev/kvm`, another says `ubuntu-26.04-arm` does not, and a GitHub reply says the Arm fleet does not surface it. They conflict. The workflow's Firecracker pin is x86_64 only.
- Firecracker's own CI uses `.metal` instance types because EC2 supports KVM only on some kernels. Host kernel support (kernel-policy.md): 5.10, 6.1, 6.18.

## Owner steps

1. **Try the plain hosted runner first.** Push the branch, then Actions, workflow `firecracker`, Run workflow, runner input left at `ubuntu-24.04`. It costs nothing on a public repo and settles the question T00 left open.
2. **Read the `/dev/kvm` line.** Open the job log, step "Is there a /dev/kvm?". Present: a line like `crw-rw---- 1 root kvm 10, 232 ... /dev/kvm` followed by `RESULT: /dev/kvm PRESENT`. Absent: `ls: cannot access '/dev/kvm'`, `RESULT: /dev/kvm ABSENT`, a red error annotation "No /dev/kvm on this runner", and the job stops there. The step also prints the count of `vmx`/`svm` CPU flags and the loaded `kvm` modules. The same text is stored in the artifact as `firecracker-kvm.txt`.
3. **If absent, use a KVM-capable runner.** Two options, neither tried here: (a) a GitHub larger runner (paid; I did not read their docs, so whether they expose `/dev/kvm` is not known); (b) a self-hosted Linux x86_64 runner on a host with KVM (bare metal, or a VM with nested virtualization on; run `ls -l /dev/kvm` on it first). Give its label in the `runner` input. The job needs `sudo`, `apt-get`, `curl` and `setfacl`; a self-hosted box needs the same.
4. **Commit the result.** Download the artifact `firecracker` and put `firecracker-run.json`, `firecracker-kvm.txt` and `firecracker-guest-sha256.txt` into `packages/guard/results/` (the `firecracker-run.json` from this machine, status `unavailable`, gets overwritten). Tick T11 only if `firecracker-run.json` says `status: pass`, shows `firecracker_version`, its `console` shows the fixture lines with a `kernel=Linux 6.18...` line, and the KVM text says PRESENT.
5. Expect to fix the first run. See the list below.

## Gap that T13 will hit: the escape suite on this tier

`guard escape --tier firecracker` needs a launcher: a command prefix that takes `sh -c <probe>` and gives the guest `/work` (rw) and `/checks` (ro). It does not exist. `guard firecracker-run` runs one fixed fixture, not arbitrary probes, so the escape probes are **not** run in a microVM by anything in this repo. Row C of the ablation cannot report "escape probes passed" until such a launcher is built and run on a KVM host.
