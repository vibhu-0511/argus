# P5.5 waves and rules for every task session

Source of truth for the tasks: `phases/P05.5-argus-skills.md` (acceptance criteria, Break it cases, ablation table) and `TASKS.md` (checkboxes). Integration branch: `stack/p5.5-skills`, cut from `origin/main` at the merge of PR #11 (P0 to P5). P5.5 gets its own pull request. It never contains the P5 multimodal follow-up (T20) or anything from `stack/p6-flow`.

## Waves

A wave is a set of sessions that run at the same time, on disjoint files. The next wave starts when the one before it is merged into `stack/p5.5-skills` and its tests pass.

| Wave | Sessions (tasks in order inside a session) | Why they can run together |
|---|---|---|
| 1 | A: T00, T01 (docs only) · B: T03 (split script in `packages/skills`, test) | Docs against a script in a new folder. |
| 2 | A: T02 (skill loader and `load_skill` in `packages/fix-loop`) · B: T04 (collect at least 20 successful trajectories on train tasks, real Claude-session runs, only after the owner says yes) | T02 touches `fix-loop/src`; T04 only drives existing code and stores runs. |
| 3 | A: T05 (draft script), then T10 (trust controls, needs the T02 loader) · B: T12 (skill lint CI, no model) | T05 and T10 are in one session because both build on the loader and the drafts; T12 is a script and a workflow. Then the owner reviews the drafts (T06). |
| 4 | T07 selection test · T08 ablation (real runs, owner yes first) · T09, T11 ADRs · T13 to T16 break-its | Need reviewed skills (T06), the loader (T02) and the trust controls (T10). |
| 5 | T17 README and phase report, final architecture, PR description | Needs everything. |

T06 is a human task: the owner reviews and edits at least 5 draft skills. The orchestrator prepares drafts and stops after wave 3 until the owner has done it. No session marks a skill reviewed or ticks T06 for the owner.

T04 and T08 are real model runs with Claude sessions as the model (one fresh subagent per loop step, sonnet strong, haiku cheap, at most 4 coordinators at once). They start only after the owner answers yes to a cost estimate. Method and hazards: `docs/notes/p5-t14.md`, `docs/notes/p5-t14-results.md`, `packages/eval/swarm/`, `packages/eval/src/eval/t14_turn.py`. Numbers come from each run's own `verdict.json` and the results files, never from a coordinator's text. A stuck run is never reset or deleted; it is reported. Two actors never work on one run folder. Docker Desktop is never restarted (another session grades images on this machine).

## Decisions fixed here so sessions agree

- Held-out set: the seeded tasks in `packages/bench/tasks/seeded` (30 directories; `bug-17` no longer applies to platform HEAD, so 29 run, as in P5-T14). The split file lists all 30 and flags the 29 runnable.
- Train set: drawn from the generated mutants in `packages/bench/tasks/mutated`.
- Skills live in `packages/skills/skills/<name>/SKILL.md` (agentskills.io format). The loader, `load_skill` and the trust checks live in `packages/fix-loop/src/fix_loop/skills.py`. The hash pins live in `packages/skills/skills.lock.json`. T01's notes may refine this; the file names above are the default.
- A draft skill is marked unreviewed; the loader refuses unreviewed skills. Only the owner flips that flag.

## Rules for a task session

1. Work in your own worktree. Touch only the files your task needs. Another session is editing other files at the same time.
2. Read `phases/P05.5-argus-skills.md` for your task rows. The acceptance criteria are the definition of done. Check each with a command and keep the output.
3. Follow the repo style: small modules, a module docstring, `ponytail:` comments for known ceilings, no unrequested abstractions. Python 3.12, `uv`, `pytest`. Tests need no model call and no network.
4. Run each package's tests separately: `uv run pytest packages/<name>/tests -q` (test names collide across packages). `test_ast_grep` in fix-loop already fails before P5; it is not yours.
5. One commit per task. Heavy data (stored runs) goes in its own commit. Do not push. Do not open a PR.
6. Commit message format (plain language, bullets, no jargon without a gloss):

   ```
   <One plain sentence ending with a full stop, same style as "Add local pgvector search over Canvas files.">

   - What changed, in one line per bullet.
   - Why it matters or how to use it.
   - Task: P5.5-Txx
   - Tests: <command> -> <result>

   Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
   ```

7. Architecture grows with each task. In the same commit, add a section `## P5.5-Txx <title>` to `docs/architecture/p5.5.md` with: the new components (name and one line), the links to existing components (name -> name), the files, and the command that proves it. Do not edit `docs/architecture/overview.md`; the orchestrating session folds the sections into it after each wave.
8. Tick the task's checkbox in `TASKS.md` only when every acceptance criterion holds. Do not tick one you could not meet; write the gap in `docs/notes/p5.5-<task>.md` instead.
9. Never ask for, print, store or log a key or token. Do not claim anything that was not run. Never invent a number.
10. Final message: tasks done, commit hashes, test output, and anything not done or not verified, plainly.
