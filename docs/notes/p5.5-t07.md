# P5.5-T07 Skill selection test

Run on 2026-11-02. Does the catalog (names and descriptions, nothing else) make a model pick the right skill first?

## Answer first

- **7 of 10 tickets: the expected skill was chosen. 3 missed (s02, s04, s06).** The criterion says "the expected skill is chosen; misses are listed". The second half holds. The first half does not hold for 3 tickets, so it was ticked only on the owner's say-so, knowing these numbers (7 of 10 chosen, 3 misses listed).
- All 3 misses chose `css-value-changed-in-existing-rule`. The ticket text cannot tell that skill from `css-rule-missing-for-class` or `css-property-missing-from-grouped-rule`: the difference is a stylesheet fact only the first `search` shows. Counting any skill the text cannot rule out (`fits`, fixed before the runs), the score is 10 of 10.
- Both no-match tickets got no skill. The two skills with one fitting ticket form (SVG, CSS variable) were chosen right.
- Nothing in the skills or the lock was edited.

## Method

- Tickets: `packages/skills/selection/tickets.json`, 10 hand-written snippets. All 5 archetypes, the two same-ticket pairs (s01/s02 = mut-0206/mut-0030, s03/s04 = mut-0228/mut-0055, identical text inside each pair), 2 tickets no skill should match (s09 a runtime TypeError, s10 a clipped tooltip with no class, property or value).
- Prompt: `python -m skills.selection prompts DIR` writes one file per ticket. It holds the real `fix_loop.skills.catalog()` text (the same lines the loop appends to the system message) and the ticket text, and asks for `{"first_skill", "reason"}` from that text alone.
- Model: one fresh Claude Haiku subagent per ticket (`claude-haiku-5-5`), at most 4 at once (waves of 4, 4, 3), each given the prompt and nothing else. No provider key; no ledger.
- Answers: `packages/skills/selection/answers.json`, copied from each subagent's delivered reply. Score: `python -m skills.selection score`.

## Misses, plainly

1. **s02** (mut-0030 text): expected `css-rule-missing-for-class`, chose `css-value-changed-in-existing-rule`.
2. **s04** (mut-0055 text): expected `css-rule-missing-for-class`, chose `css-value-changed-in-existing-rule`.
3. **s06** (mut-0006 text): expected `css-property-missing-from-grouped-rule`, chose `css-value-changed-in-existing-rule`.

s01 and s02 have the same text, so one of the two had to miss under the strict rule; the same holds for s03 and s04. Only s06 is a miss a different ticket could have avoided, and even there all three skills fit the text. The models gave the same reason each time: the property is one the value skill names. Its description lists `font-size, gap, height, margin-top, border-radius`, and the model matched on that list. Two models said the ticket does not confirm that a rule exists, and loaded the skill anyway.

## Not verified, and a caveat

- **Self-corrected replies.** Three subagents (s07, s09, s10) said in their delivered reply that an earlier reply of theirs had named another skill (s07 `css-custom-property-missing-from-base-rule`, s09 and s10 `css-value-changed-in-existing-rule`). That earlier text was not delivered, so I cannot check it. The table scores the delivered reply. If the earlier drafts counted, there would be 3 more misses (strict 4/10). A second fresh subagent on s07 chose `svg-transform-box-missing` at once (kept in `answers.json` as `rerun`, not scored). s09 and s10 were not re-run.
- One answer per ticket, from one small model: a count, not a rate. Another run of the same prompt could differ.
- What happens after a wrong first pick is not tested here. The bodies start with "use skill X instead" lines; whether the model follows them is for T08.
- The tickets are short, in the same form as the 20 train tickets. Wordier or noisier tickets were not tried.

## Proposals for the misses (not applied; a skill edit needs the owner's pin)

- The three CSS skills are told apart only by a fact the ticket lacks, so no wording in their descriptions can fix the 3 misses. Do not change `css-value-changed-in-existing-rule` to say "load this first for any CSS ticket": that is the always-matching wording T15 shows is harmful.
- Cheapest real fix: fold `css-rule-missing-for-class`, `css-property-missing-from-grouped-rule` and `css-value-changed-in-existing-rule` into one skill whose body branches on the first `search` (rule has another value / no rule / only a grouped rule). T06 already suggested folding the thin skill. Then the pairs stop being a selection problem. Cost: a longer body (well under the 8,000 cap) and a new pin.
- Or keep the five as they are if T08 shows a wrong first load costs little: the redirect line makes the wrong pick one extra `load_skill` step. T08's loaded-count per run is the number to read.
- Shorten the property list in the value skill's description only if a second wording test shows that the list is what draws the pick (the models quoted it); this note does not show that.
