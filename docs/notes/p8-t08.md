# P8-T08 Ticket intake

A labelled issue starts one workflow. Code: `packages/flow/src/flow/intake.py`, wired in `flow.webhook.create_app(on_intake=...)` and `flow.service`. Tests: `packages/flow/tests/test_intake.py` (19 tests, mock GitHub, no network, no model).

## Where it lives, and why

In `flow`, not in `packages/app`. The webhook endpoint, the delivery dedup, the workflow id contract (`flow.enqueue`) and the installation tokens (`flow.installations`, P8-T03) are all in `flow`, and `argus-app` depends on `flow`, not the other way round. Intake is a new handler on the same endpoint, so it reuses `enqueue_reconcile` and the 202-first rule (ADR-021).

## How each criterion is met

| Criterion | How | Test |
|---|---|---|
| Adding the label starts exactly one workflow | `issues` / `labeled` with the intake label (default `argus`, env `ARGUS_INTAKE_LABEL`, case-insensitive) calls `enqueue_reconcile("owner/repo#number")`. The ticket id is the only workflow key, so the workflow id is the idempotency key | `test_the_label_from_a_user_with_write_access_starts_one_workflow` |
| Redelivery of the same event | `HintDedup` on `X-GitHub-Delivery` drops it before the permission call | `test_the_same_delivery_twice_is_one_workflow_and_one_permission_check` |
| Label removed and added again, or added by a second person | new delivery ids, same ticket id, same workflow id: still one workflow | `test_the_label_added_again_is_still_one_workflow` |
| A label by a user without write access is ignored | `GET /repos/{repo}/collaborators/{login}/permission` with a read-only installation token; only `admin`, `maintain`, `write` pass (`role_name` first, so `triage` is refused) | `test_a_label_from_a_user_without_write_access_is_ignored_and_logged` (triage, read, not a collaborator) |
| The ignore is logged | structured log line `intake_ignored {"actor","label","reason","ticket"}` and, when an audit sink is given, an `intake_ignored` record in the guard hash-chained audit log. The test reads both and checks the chain with `guard.auditlog.verify` | same test |
| A failed check does not let the label through | any error in the lookup (HTTP 500, repo without the App, network) is a refusal and is logged; the delivery id is forgotten so a manual redelivery works | `test_a_failed_permission_check_refuses`, `test_a_repo_without_the_app_is_refused_before_any_http_call` |
| Webhook stays a hint | the handler answers 202 and runs intake after the response; the test drives the ASGI app and checks the order `response 202`, then the GitHub call | `test_the_answer_is_sent_before_the_permission_call` |

With intake on, an `issues` event that is not `labeled` is ignored (an opened or edited issue without the label must not start a workflow). With intake off (`on_intake` not given, or the App not configured) the P6 behaviour is unchanged (tested).

## Not done, not verified

- Never run against a real App or a real label event. The permission answer shape (`permission`, `role_name`) is from the GitHub docs, mocked. `role_name` for a fine-grained role is not exercised.
- `flow.service` turns intake on only when `ARGUS_GITHUB_APP_ID` and `ARGUS_GITHUB_APP_PRIVATE_KEY` are set. The audit sink is not wired in the service (Render's disk is not kept); there the structured log line is the record.
- A finished workflow is not restarted by a new label (same workflow id) until a deliberate re-run with an attempt number exists.
