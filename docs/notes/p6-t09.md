# P6-T09 MRTR elicitation for the QA approval step

Date: 2026-11-01. `mcp` 2.3.0 (pinned `mcp==2.3.0` in `packages/flow/pyproject.toml`, same pin as `dom2src-mcp` and `repro-agent`; `uv.lock` gained two lines, `uv lock --check` passes). Spec 2026-07-28. Architecture: [docs/architecture/p6.md](../architecture/p6.md), section P6-T09. Background: [p6-t01-dbos-mrtr.md](p6-t01-dbos-mrtr.md) section 5.

T01 left one thing open: "whether the Python SDK 2.3.0 ships helpers for either feature: not confirmed". Answer, from reading the installed SDK (`mcp/server/mcpserver/resolve.py`, `request_state.py`, `tools/base.py`, `client/_input_required.py`) and from running it:

## What the SDK 2.3.0 does server-side

- It builds MRTR itself. A tool parameter written `Annotated[ElicitationResult[Model], Resolve(fn)]`, where `fn` returns `Elicit(message, Model)`, makes the SDK return `InputRequiredResult` on round one and run the tool body only when the retry carries the answer. A tool can also return `InputRequiredResult` itself (`ctx.input_responses`, `ctx.request_state`), but not together with `Resolve` parameters. We use the resolver form.
- Wire shape seen in the test (round one): `resultType: "input_required"`, `inputRequests: {"flow.qa_mcp:ask": {"method": "elicitation/create", "params": {"mode": "form", "message": ..., "requestedSchema": {...}}}}`, `requestState: "v1...."`. The key is chosen by the SDK from the resolver's module and name. The retry sends `inputResponses: {"flow.qa_mcp:ask": {"action": "accept", "content": {...}}}` and the echoed `requestState`.
- `requestState` is sealed by default (AES-256-GCM under a process-local key, 600 s TTL, bound to the request and the audience = server name). A state with its last characters changed is refused with `MCPError "Invalid or expired requestState"` and the tool does not run (test). Consequence: with the default key a state minted before a restart or by another worker is refused. `RequestStateSecurity(keys=[...])` would share a key between instances; not needed for one Render instance, and the key would be an environment variable, never a file.
- A retry with no `inputResponses` is answered with the question again, not an error (test), as the spec asks.
- The question must render identically on every round (the SDK checks it), so `ask(ticket_id)` uses the ticket id only.

## What was NOT verified

- No real MCP host was run: not Claude Desktop, Claude Code, Cursor, VS Code or any other product. All "client" behaviour above is the `mcp` SDK's own `Client` talking to the server in the same process over its in-memory transport. Whether any shipping host declares the elicitation capability, speaks 2026-07-28 or shows the form to a person is unknown from this work.
- No transport was run over a socket or a pipe. The server object is built (`flow.qa_mcp.qa_server`); serving it over HTTP inside the FastAPI app or over stdio is not done here (T12 deploys the app). The dom2src server in this repo is stdio-only and rejects clients below 2026-07-28; this server does not add that veto, so older clients are served by the legacy path above.
- The wire JSON was read from the SDK's own models (`model_dump_json(by_alias=True)`), not from a captured socket trace and not checked against the spec's JSON schema file.
- Time limits: nothing here tests a human taking minutes or hours between rounds. The sealed state expires after 600 s, so a reviewer who answers later gets "Invalid or expired requestState" and must call again. This is one more reason the durable wait stays in DBOS and the review-comment path (T10) stays as the fallback.

## Decisions

- Idempotency key: `qa_signal_key(ticket, "mrtr", <JSON-RPC request id>)`. The id is the SDK client's counter; two clients can reuse an id. A reuse for the same ticket is the same key and is dropped, which is also what the state machine does with any second signal.
- `by` is the fixed string `mcp-client`: the MCP request carries no verified person. Unlike T10, this path has no allowed-reviewer list; whoever can reach the MCP endpoint can answer. Put authentication in front of it before it is exposed (T12).
- The tool asks before it checks that the workflow exists (a `ponytail:` note in the module).

Run it: `uv run --all-packages python -m pytest packages/flow/tests/test_qa_mcp.py -q` (no database). With `ARGUS_FLOW_DATABASE_URL` set, `test_workflow.py` also resumes a real waiting workflow through the tool.
