# P7-T13 Ablation: Docker vs gVisor vs Firecracker

**State: not done. The box stays unticked.** The acceptance criterion needs rows A and B filled from real runs; row C from a real run, or left empty when the Firecracker cut is taken. Row A has a real run. Row B has none (no `runsc` on this machine). Row C has none (no KVM, and the microVM tier has never booted).

## What is built and tested

`guard ablation --tier docker|gvisor|firecracker [--n 30] [--out FILE]` in `packages/guard/src/guard/ablation.py` (registered in `cli.py`, 4 lines). For a tier it:

1. starts the sandbox container N times (default 30) with the fix-loop flags (`fix_loop.sandbox.docker_argv`: `--network none`, 1 CPU, 512m, `/checks` read-only) and the fixture from `guard sandbox-run`, each with its own name `guard-abl-<tier>-<random>`, removed afterwards; each start is judged by the same check as `guard sandbox-run`, and a start that fails the check is listed, not counted;
2. records per start the cold start (time from the `docker run` launch to the first line the fixture prints) and the fixture run time (first line to exit and removal), and gives n, p50, p95, min and max in ms (nearest-rank percentile);
3. runs the 12-probe escape suite on the tier and records probes passed of total;
4. checks that no `guard-abl-<tier>-*` container is left;
5. writes `packages/guard/results/ablation-<tier>.json`.

A tier that cannot run is written with `status: not_run`, `detail: "not run: <reason>"`, no numbers, and the command exits 3. Tests: `packages/guard/tests/test_ablation.py` (10 tests; the percentile math, the timing code on a real child process, the argument list, the not-run paths, a failed start). No Docker needed.

How to read row A. The machine is Windows 11 with Docker Desktop, so Linux containers run inside a WSL2 VM and the cold start includes that boundary. It is **not comparable with a Linux runner**. It is one run with N = 30 and no confidence interval, taken while other sessions may have been using the machine (load not measured). "Run-time overhead" in the phase table is the fixture run time after the first line; there is no bare-host baseline here, so it is not a ratio. The earlier single `runc` sample in `docs/notes/p7-t10.md` (1.089 s wall for one run) was a different measurement: it timed the whole call on a cold daemon, and one sample is not a p50. No conclusion about the best tier is drawn here.

## Owner steps

**Row B (needed to tick T13).**

1. On a Linux host (Linux 5.6+, x86_64 or ARM64) with Docker, install and register `runsc` by the steps in [p7-t10.md](p7-t10.md) (or run the manual workflow `.github/workflows/gvisor.yml` and look at its log). Check `docker info --format '{{json .Runtimes}}'` lists `runsc`.
2. On that host run, and keep the output:

   ```bash
   uv sync --all-packages --locked
   uv run --all-packages guard ablation --tier gvisor --n 30
   ```

   The file `packages/guard/results/ablation-gvisor.json` must say `status: done`. Look at `escape.probes_passed` and at `starts_failed`.
3. **Run tier A on the same host** (`guard ablation --tier docker --n 30`) and use that file for row A. The Windows numbers for A and a Linux number for B would compare two different machines. Keep the Windows file under another name (for example `ablation-docker-windows.json`) and say so in the phase doc.
4. Fill row B (and replace row A) in the Ablation table of `phases/P07-argus-guard.md` from the JSON, and update the statement under the table: machine, kernel, N, and whether gVisor used its default platform (see p7-t10.md).

**Row C (or take the cut).**

- Either take the Firecracker cut: leave row C empty and let ADR-025 (T15) say why (no KVM runner available, or KVM absent on the hosted runner). The acceptance criterion allows this.
- Or fill row C. It needs, in order: a KVM runner and a real boot ([p7-t11.md](p7-t11.md)); a launcher for `guard escape --tier firecracker` (a command prefix that takes `sh -c <probe>` and gives the guest `/work` rw and `/checks` ro; not built); and a cold-start harness for the microVM (N boots, time from the Firecracker launch to the first fixture line on the serial console; not built, `guard firecracker-run` times one boot only). Then `guard ablation --tier firecracker` has to be extended to call them; today it always writes `not_run`.

**Then tick T13** only when `ablation-docker.json` and `ablation-gvisor.json` both say `done` (from the same host) and row C is either from a real run or the cut is recorded.

## Not verified

- Anything under gVisor or Firecracker: no number exists for either.
- The ablation run on a Linux host, any repeat of the whole run, the variance between runs.
- `guard ablation --tier gvisor` when `runsc` is present: the code path (the `--runtime runsc` flag, the escape suite on that tier) is covered by tests with Docker replaced, not by a run.
- Whether the fixture is a good stand-in for a real fix-loop task: it is a few `echo` and `cat` commands, so the run-time overhead of heavier tiers on real work is not measured.
