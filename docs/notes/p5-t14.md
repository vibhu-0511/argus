# P5-T14 routing ablation: harness built, nothing run

Written 2026-11-01. **No model call was made. No number in the Ablation table of `phases/P05-argus-eval.md` is measured**; the table there still holds dashes, and T14 is not ticked. What exists is the wiring, the two policies, the agent factories, the table script and a stub-model proof. The stub figures (`"stub": true` in the agent params) measure nothing; `python -m eval.ablation table` prints a STUB banner above them.

## What was built

| Piece | Where |
|---|---|
| `run_fix` and `run_repro` take `router=` and `stage=` (defaults `fix`, `repro`); each step stores `tier`, `host`, `model`; the router's ledger call is the only one (no second count); no router, no change | `packages/fix-loop/src/fix_loop/loop.py`, `packages/repro-agent/src/repro_agent/loop.py` |
| Variant A as data: all stages on the strong tier. Variant B: `argus_core/routing.yaml` untouched | `packages/eval/policies/strong-only.yaml` |

| `Outcome.dollars`: a routed run spans two priced models, so the agent prices its own tokens and the runner sums them. Without it `$_equivalent` would price every token at `config.model` | `packages/eval/src/eval/runner.py` |
| `python -m eval.ablation table A.json B.json` and `tasks --out F` | `ablation.py` |
| Tests, stub models only | `packages/fix-loop/tests/test_router_wiring.py`, `packages/repro-agent/tests/test_router_wiring.py`, `packages/eval/tests/test_ablation.py`, `packages/eval/tests/test_ablation_run.py` |

What the stub run proves (`test_ablation_run.py`, 4 tasks, both variants through `python -m eval run`): the same task list for both; A's steps are all `strong`, B's repro steps are `cheap` and its fix steps `strong`; cached tokens are kept apart from fresh ones and sum to the trajectory steps; `$_equivalent` equals the per-model sum from `prices.json` (B cheaper than A for the same tokens); quota charge per model recomputed from the trajectories equals the ledger file's `tokens`, `requests` and `cached` for every model. That last check is why the table can compute quota share from trajectories: the ledger file resets each UTC day, so on a multi-day run it holds only the last day.

How the table is read (for the real run): per bug = per scored task (`resolve_rate.total`). **Quota share/bug** = the largest, over the models a variant used, of (tokens charged to that model) / (its `tokens_per_day` in `docs/quotas.md`) / bugs. Charged = in + out, minus cached tokens where the file says cached do not count (all three Groq rows say they do not). It is a share of one day's cap, so 50% means two bugs per day. Requests per day (1000) are not in the cell; the by-tier lines under the table show calls. A dash appears when a stage trajectory is missing or the steps do not add up to the results file's totals.

## What blocks a real run (none of these was built; each is the owner's call)

1. **No live tree runner for the repro stage.** `run_repro` needs `run_trees(script) -> TreeRun`, which runs the script on the buggy and the golden tree. The repo has the Docker image and `verify.py` (which classifies two results) but no Python function that does this against the app; the repro batch uses recorded fixtures. Without it variant B equals variant A (the fix stage is strong in both). The factory refuses a live run without `params.run_trees` (`module:function` returning the runner) before it touches a task. `repro: false` would also run, but then the two variants are the same experiment.
2. **`localize` makes no chat call.** It is in both policies, but dom2src locates with embeddings. The fix prompt says `Locate: none`, as in P3/P4. So B can only move the repro stage to the cheap tier.
3. **No pacing.** The ledger refuses a call that would pass a cap and the loop treats that as the end of the task (`quota_exceeded`); it does not wait. Groq's rows are 8000 tokens per minute and 30 requests per minute. A stub run against the real rows with no delay hit the 30-request cap after 30 calls and the other tasks stopped. A live run needs a wait-and-retry layer in front of the router (not in the ledger or router, both wave-2 code).
4. **No day-boundary handling.** At 200,000 tokens per day a run takes several days (below). The runner runs all tasks in one process and has no resume. A task caught by the daily cap ends as `quota_exceeded` and counts as unresolved. Either chunk the task list by day (and merge the results files, no merge tool exists) or add a wait at the cap.
5. **A and B share `openai/gpt-oss-120b`.** Use one `params.ledger` file for both, run them one after the other, not at once (the ledger has one writer). Two ledgers would each believe the full 200,000 tokens is free.
6. **The Mistral fallback has no quota row** (`docs/quotas.md`), so the ledger refuses it before any call. A quota refusal on Groq therefore ends the task, as `routing.yaml` already says. The Ollama fallback needs a quota row too.
7. **Cached tokens have never been seen from Groq** (`docs/quotas.md`, probe of 2026-10-29), so a real cached count may be 0 for both variants.
8. **Task count.** The phase file says a 30-task subset. The seeded bench has 30 directories, and `bug-17` no longer applies to platform HEAD (`docs/notes/p4-finish.md`), so `tasks` writes 29 (`--exclude` changes this).
9. **Host choice.** The policy models must have a row in `prices.json` (else `$` is a dash) and in `docs/quotas.md` (else the ledger refuses them and quota share is a dash). The P3/P4 Claude-session driver (`fix_loop.turn`) answers one turn per call and is not a callable client, so using Claude sessions as the strong tier needs a relay client (like `packages/fix-loop/swarm/mini/relay.py`) passed through `params.clients`, a self-imposed budget row in a quotas file, and a price row. Not built.

## Tokens per task against the Groq limits

Source: the stored P4 context-strategy runs (`docs/notes/p3-finish.md`, section "Full run", `p4b-full-*`): 29 seeded tasks, one run per cell, a Claude session as the model, **tokens are chars/4 estimates of the messages**, cached 0. The 32,000-token context budget is the one those runs used (`fix_loop.turn.BUDGET_DEFAULT`); a strategy runs once cumulative use passes 80% of it. These are the only token counts for a whole 29-task fix run that exist. A weaker model (gpt-oss) may need more turns, and with no compaction each extra turn re-sends the whole context, so treat the rows as a floor for the fix stage, not a forecast.

| Strategy at 32,000 | In / out per task | Model turns per task | Peak request (mean per task / max) | Requests over 8,000 tokens (26 stored runs) |
|---|---|---|---|---|
| none | 100,467 / 170 | 6.24 | 34,060 / 484,541 | 48% |
| cap (8000-char output cut) | 43,105 / 200 | 7.55 | 7,276 / 18,118 | 29% |
| offload | 32,430 / 228 | 8.97 | 5,505 / 14,400 | 13% |
| summary | 23,485 / 250 (summarizer calls not counted) | 13.31 | 5,180 / 8,339 | 4% |

The last column is my count over the `p4b-full-*` trajectories, not a figure from the earlier write-up.

Limits (`docs/quotas.md`): per model 8,000 tokens per minute, 200,000 per day, 1,000 requests per day. Tokens per minute and requests per day are header measurements; tokens per day (200,000) and requests per minute (30) are the published table.

- **One request can exceed the per-minute cap.** With `cap`, about 3 in 10 requests are over 8,000 estimated tokens. I expect Groq to refuse a single request larger than the per-minute cap, but that was not probed (the 2026-10-29 probe sent one tiny call per model). Only `summary` keeps nearly all requests under it.
- **The daily cap is what limits the run, not requests.** 29 tasks: `cap` 1.26 M tokens, 219 requests; `offload` 0.95 M, 260; `summary` 0.69 M (undercounted), 386; `none` 2.92 M, 181. Requests stay far under 1,000 per day.
- **Days for 29 tasks, fix stage on one model at 200,000 tokens per day** (my arithmetic from the table; rounded up to whole days):

| Strategy | Days for one variant | Days for A then B (same model) |
|---|---|---|
| none | 15 | 30 |
| cap | 7 | 13 |
| offload | 5 | 10 |
| summary | 4 (more with the summarizer calls) | 7 |

- **Routing changes the day count very little.** The repro request is the ticket text plus one instruction, 40 to 262 estimated tokens over the 30 seeded tickets (mean 53), and the model returns a script. I guess a repro stage at no more than about 2,000 tokens per task including retries, about 60,000 tokens over 29 tasks, or 0.3 of a day on the 120b model in A and none in B. That guess is not measured, and a repro prompt that carries page structure would be larger. The fix stage, 24,000 to 100,000 tokens, is on the strong model in both variants, so B can save roughly 0.3 day out of 7 (cap), and the hypothesis (tokens and quota per bug fall) will show up as a few percent at most unless the repro prompt grows.
- **Pure wait time at 8,000 tokens per minute** is short next to the daily cap: `cap` 1.26 M tokens is about 157 minutes per variant.
- **List-price equivalent** at the `prices.json` gpt-oss-120b rates (0.15 / 0.60 USD per million): about 0.19 USD for 29 tasks at `cap`, 0.15 `offload`, 0.11 `summary`, 0.44 `none`. The cost is cents; the constraint is the free-tier caps and whether a plan with higher limits is available (not checked here).

Ways to run it, for the owner to choose:

1. **Groq free tier as is:** about 13 days for both variants at `cap`, after pacing and day-chunking are written (blockers 3, 4) and the tree runner exists (1).
2. **A host with higher limits** (a paid Groq or Mistral plan, or an Anthropic key): add its models to `routing.yaml` and `strong-only.yaml` (the strong tier line must match in both; a test checks it), a row in `docs/quotas.md` and in `prices.json`. Then blockers 3 and 4 mostly go away and a variant runs in hours. Quota share needs a cap to divide by; if the host publishes none, that cell stays a dash.
3. **Claude sessions as the strong tier:** needs the relay client in blocker 9. Slow (one session per turn), no real quota, and the cheap tier is still Groq's 20b.

## Claude-session driver and dry run (2026-11-01)

The owner chose Claude sessions as the model for the real runs: all 29 runnable seeded tasks (`bug-17` out), two variants, **A** = every stage on the strong tier, **B** = routed (repro on the cheap tier, fix on the strong tier). Tiers are subagent models, set per stage through the Agent tool's `model` parameter: **strong = `sonnet`, cheap = `haiku`**. Results are labelled `claude-session tiers`; the ids in the policies (`claude-sonnet-5-5`, `claude-haiku-5-5`) are the API ids of those families, and the driver cannot see which concrete model an alias resolved to. Nothing below changes the Groq route in the first half of this file; blockers 1, 2, 5 and 9 are answered for this route only:

|---|---|

| 2 `localize` makes no chat call | **Still true, and it limits what the result can show.** See "What the results will not show". |

### What was built

- **Repro tree runner.** `python -m repro_agent.trees up|down|status|run`. It serves the platform's Canvas with Vite on `127.0.0.1` (the checkout is only read; the Vite cache goes to the temp dir) and starts a small proxy container, so the sandbox container runs on an **internal** Docker network (`argus-t14-net`: the app is reachable, the internet is not) using the existing `argus-repro:p1` image. Per script, one container runs it on both trees (`rig/run-script.mjs`) and `verify.verify` classifies the two results. The trees are the buggy and golden **CSS** (the seeded bugs are CSS mutations): `bug.patch`, then `golden.patch`, applied to the files' text at platform HEAD and swapped into the page in the browser. `eval.ablation`'s `params.run_trees` now takes `repro_agent.trees:live` (a function from task directory to runner).
- **Pipeline.** `python -m eval.t14_turn start|show|answer|status|results` (`packages/eval/src/eval/t14_turn.py`): `run_repro` (stage `repro`), then `run_fix` (stage `fix`, strategy `cap`, budget 32,000, the Groq config's suggestion), both through a `Router`. Each driver call replays from `answers.jsonl` and ends at the first model call with no stored answer. Every stored answer and every trajectory step carries stage, tier, host and model. Layout: `packages/eval/runs/t14/<A|B>/<task id>/{repro,fix}/trajectory.jsonl`, `answers.jsonl`, `verdict.json`, `diff.patch`. The status line printed after each answer names the next worker's model (`worker_model=haiku|sonnet`) or is the verdict.
- **Swarm scripts** (`packages/eval/swarm/`): `turn.sh`, `repro-rig.sh`, `start_task.sh`, `status.sh`, the worker instructions `step.md` and the coordinator instructions `coord_ablation.md`, which make the coordinator set `model` on every step worker from the status line.
- **Price row** `claude-haiku-5-5` in `prices.json`: USD 0.10 in, 0.50 out, 0.01 cache hit per million tokens. Read on the vendor page on 2026-11-01 (`platform.claude.com/docs/en/about-claude/pricing`, the row "for prompts up to 100,000 tokens"; the page shows display names, not API ids). Prompts over 100k cost more (0.50 / 2.50 / 0.05); no run here sends one. The sonnet row was already there.
- **Self-imposed budget.** `eval.t14_turn.SELF_IMPOSED` (300 requests, 10 million tokens), one entry per tier model, because the ledger refuses a model without a row. It never binds (a fresh ledger per call) and is **not** a provider limit. `docs/quotas.md` got no Claude row, so the table's quota-share cell is a dash for these runs.
- **Results.** `python -m eval.t14_turn results <A|B> --tasks packages/eval/runs/ablation-tasks.json --out packages/eval/results/ablation-<A|B>.json` folds the finished runs (same task list for both; a task with no verdict becomes an `error` row, never a gap). `python -m eval.ablation table A.json B.json` prints the table, with a banner for claude-session runs. Tokens split by tier come from the trajectories. **Tokens are chars/4 estimates** of the messages and leave out each subagent's harness overhead; `$_equivalent` is their list-price equivalent, priced model by model; latency is the task's wall clock, with several tasks running at once.

### Steps for the 58 runs

Prerequisites (this machine): `ARGUS_PLATFORM_REPO` (the scripts default it to the local checkout), Docker with `argus-repro:p1` and `argus-fix-sandbox:p3`, node, and **`node_modules` at the repo root and in `packages/bench`** of the checkout you run from (the scorer needs them; a fresh worktree has none. This worktree got two untracked directory junctions to the main checkout's folders; `pnpm install --frozen-lockfile` does the same job).

1. `bash packages/eval/swarm/repro-rig.sh up` (the rig is **up now** from the dry run; `status` shows it, `down` stops it).
2. `uv run --frozen --all-packages python -m eval.ablation tasks --out packages/eval/runs/ablation-tasks.json` (29 tasks: `seed-e01` to `seed-e10`, `seed-m01` to `seed-m09`, `seed-h01` to `seed-h10`).
3. Per task, both variants: `bash packages/eval/swarm/start_task.sh A <id>` and `... B <id>` with `run_in_background` (about 10 s each when idle). Wait for them, then start one coordinator per task: Agent, `general-purpose`, `model: sonnet` (the dry run used sonnet; haiku as coordinator was not tried), prompt:
   `SWARM = <worktree>/packages/eval/swarm (/c/... form). RUNS = A-<id>, B-<id>. Read the file <SWARM>/coord_ablation.md with the Read tool and follow it exactly.`
   At most 6 coordinators at once. A coordinator starts one fresh step worker at a time, with `model` = `haiku` or `sonnet` as the status line says, and returns the verdict lines plus "sonnet n, haiku m".
4. `bash packages/eval/swarm/status.sh` shows runs started, verdicts and worker steps recorded. A run that returns "no verdict after N workers" is continued by a coordinator for that run id alone (it resumes from the stored answers).
5. When all 58 have verdicts: `results A` and `results B` (command above), then `table`; copy the two rows into the Ablation table of `phases/P05-argus-eval.md`, labelled claude-session; tick T14 only if the owner accepts a Claude-session run as meeting the task; write ADR-016 (T15).

Machine notes: run `start_task.sh` in the background (a platform worktree per run). Several scripts at once share one Vite server and run in separate containers; `run_repro` allows 300 s per script. If a script times out the repro loop stops with `tool-unavailable` and the fix stage runs with "Repro: not-run".

### Dry run: `B-seed-e01`, real subagents (the only run made)

One task, variant B, a real coordinator (sonnet) and real step workers; nothing else was launched. Files: `packages/eval/runs/t14/B/seed-e01/` (git-ignored); results `packages/eval/runs/t14-dryrun-B.json`.

- **Worker steps: 7** (3 repro on haiku, 4 fix on sonnet), **plus 1 coordinator** that used 73,213 tokens by the harness's own count (11 tool calls: it reads its instructions, runs status and starts the 7 workers). Wall clock 248 s for the task, about 35 s per step. The step workers' own token use is not visible from here; the earlier P3/P4 figure of about 70,000 harness tokens per step is only a guess for this run.
- **Verdict: resolved**, stop reason `submit`, scorer exit 0. The platform worktree was removed afterwards.
- **Repro stage: no valid reproduction.** Three haiku attempts, ending `retry-cap`: they used `getByRole('img'/'link', {name: /dcortex/i})` (the system prompt asks for `getByRole`) and asserted a size on the element they found (`width` 41.28 px; `height` 32 px; or "hidden") instead of the `.landing-brand` font size, which no role selector reaches. The script failed on both trees, so the fix stage got `Repro: not-run`. The pipeline worked as designed; the stage did not produce a repro.
- Tokens (chars/4 estimates): haiku 783 in / 171 out over 3 calls, sonnet 10,566 in / 99 out over 4 calls; `$_equivalent` 0.0223 USD (0.0002 of it haiku). The table's quota cell is a dash.
- Before the real subagents, a scripted rehearsal of the same task (canned answers, no model) proved the plumbing: a valid repro on `seed-e01` (buggy fails with `last seen "8px"`, golden passes, verdict `valid`), wrong-kind replies rejected, scorer resolved.

Estimate for the 58 runs (**my arithmetic, not measured**): the fix stage took 7.55 model turns per task on average under `cap` in the P3/P4 runs (table above), and the repro stage takes up to 3 turns when no repro is found (as here). That is about 10.5 worker steps per run, about 610 for the 58 (about 220 fix steps and up to 87 repro steps per variant). At 35 s per step and 6 coordinators at once that is roughly 1 to 2 hours of wall time if the machine keeps up. At about 70,000 harness tokens per step it would be roughly 40 million tokens in all, a wide guess (P4's per-run reports gave 70,000 to 113,000 per run of one or more steps, not per step), plus tens of thousands per coordinator.

### What the results will not show

- **Routing moves only the repro stage.** `localize` makes no chat call (dom2src locates with embeddings; the fix prompt says `Locate: none`), so B differs from A in at most 3 haiku-versus-sonnet repro turns per task. All fix turns, about 7 per task, are sonnet in both variants. Expect near-identical resolve rates and a token and $ difference of a few percent.
- **The repro stage will rarely produce a valid repro on these bugs.** The seeded bugs are CSS-property mutations (font size, flex direction, z-index, overflow, a `div.` selector); the repro prompt asks for `getByRole` with an accessible name, and CSS properties on non-semantic elements are not reachable that way. The dry run found none in three tries. So `repro_found` will probably be false for most tasks in both variants, the fix stage will mostly run with `Repro: not-run`, and the cheap-versus-strong difference in the repro stage mainly measures how often each tier guesses a selector that reaches the element. This is a property of the existing prompt, not of the driver; I did not change the prompt. I did add an app brief to the repro ticket text only (routes, how `page` starts, which `expect` matchers exist), because a model that cannot see the app cannot write a runnable script otherwise. It is the same for A and B, is my choice and not measured, and lives in `t14_turn.BRIEF`.
- **The app is a mock.** No backend: `/api` answers are the fixed mock copied from the P4 calibration renderer, signed out only on `/login`. Bugs on screens the mock leaves empty (admin tables, desk) cannot show up. Nine of the tasks do not change a static screenshot (listed in `packages/verify/calibration/README.md`); a computed-style assertion can still catch them, but the model must know the selector.
- **One run per cell, one model family.** Not comparable with the Groq rows. The cheap and strong tiers differ in capability, and the concrete models behind the aliases are not visible here. Tokens are estimates; subagent harness overhead is excluded; latency includes coordinator waits and parallel load.
- **Runner hazard, not fixed:** `eval.runner._aggregate` falls back to pricing every token at `config.model` when no task reports its own `dollars`. With an unpriced second model a routed run would show a wrong `$` instead of a dash (this showed up in a rehearsal before the haiku price row existed). With both models priced it does not bite now.
