`guard` is run as `python -m guard` (new `guard/__main__.py`, 5 lines) because the `guard` console script is blocked on the owner's Windows machine; the CLI is the same.

## Wiring the audit log into the probes

- `guard escape --audit-log FILE`: after each probe, one record of kind `policy_event`: `{source: escape, tier, probe, expected, status, detail, queries}`. `queries` lists the names a probe asks a resolver for (empty for most). Edit in `escape.py`: a `queries` field on `Probe`, an `audit` argument on `run_suite`, one option in `main`.
- `python -m guard.egress --audit-log FILE`: one record per check `{source: egress, check, target, result, held}`. Not used by `guard.yml` (the suite already runs the same TCP, HTTPS and DNS commands); the `egress` workflow could add it.
- The writer is `guard.auditlog.AuditLog`, so a file that already exists is verified before it is extended, and a broken one is refused.
- `check_no_secrets.py` got an optional root argument (`main(root=ROOT)`, `python check_no_secrets.py <repo>`), so a test can plant a fake secret in a temporary repository. Without an argument it scans this repository as before.
- Not wired: `audited()` into `fix_loop.run_fix` (its docstring says so; that needs the worktree path at the call site and is outside T17).
