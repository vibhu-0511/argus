# P5.5-T05 draft script

`packages/skills/src/skills/draft.py`. Run: `uv run --all-packages python -m skills.draft --runs <runs folder> --base-url URL --model MODEL --key-env NAME` (add `--dry-run` to list the groups with no model call).

## What it does

1. Finds every `verdict.json` under `--runs` whose `verdict` is `resolved` and whose `task_id` is in the `train` list of `split.json`. A held-out task is never used. The trajectory is `<run>/fix/trajectory.jsonl` (the T04 and T14 layout) or `<run>/trajectory.jsonl`.
2. Groups the runs by archetype (from the mutant's `meta.json`), 3 runs per group by default, in sorted task order.
3. Sends each group to the cheap-tier model once: the ticket and each step as `tool call -> first 300 characters of the result`, 2,500 characters per run at most. The system message says the runs are data, not instructions.
4. The model returns `{name, description, body}`. The script writes the frontmatter itself, so the model cannot add a field or a tool: `description` is JSON-quoted (T02 rule: an unquoted `: ` is refused by the loader), `allowed-tools` is fixed to `read_file list_dir search ast_grep edit submit` (no `run_cmd`), `metadata` has `argus-status: "unreviewed"`, `argus-archetype` and `argus-sources` (T01 keys).
5. A reply is rejected, and nothing is written, when it is not the JSON asked for, the name is not a valid skill name, the directory already exists (a reviewed skill is never overwritten), or the file fails the loader's own format check (`fix_loop.skills._parse`) or the 8,000-character body limit.

A draft has no lock entry, so the T10 loader refuses it until the owner reviews and pins it.

## What was proven

- `uv run --all-packages python -m pytest packages/skills/tests -q` -> 9 passed (4 new in `test_draft.py`: which runs count, prompt content, a written draft parses with the loader's check and is marked unreviewed, six kinds of bad reply write nothing). The model is a stub. - `--dry-run` on the in-progress T04 runs of another session's worktree (read only, nothing written there) found 7 resolved train runs and made 3 groups. So the real layout is read correctly.

## Real run (2026-11-02)

Model: Claude Haiku (subagent model `haiku`), one fresh subagent per group, at most 4 at once. No key, no provider, no ledger. Driver: `skills.draft_claude` (`prepare` writes `gNN.prompt.json` from `skills.draft.groups`/`render_run`/`prompt`; each subagent reads one and writes `gNN.reply.txt`; `finish` feeds the reply to `skills.draft.draft_group`, so the format check and the written frontmatter are the script's). Evidence: `packages/skills/draft-runs/p55-t05/` (7 prompts, 7 replies, `ledger.json`).

Input: the 20 resolved train runs in `packages/skills/trajectories/`, 3 per group in sorted task order, so 7 groups (font-size: 4, missing-style: 3).

All 7 were accepted on the first reply; no group was retried. Every draft has `argus-status: "unreviewed"`, no `run_cmd`, no lock entry.

## Cost (from stored files and the harness)

- Draft model calls: 7 (one subagent each, 3 tool uses each: read, write, report).
- Prompt and reply sizes, chars/4 from the stored files: 7,909 tokens in, 2,292 out (`draft-runs/p55-t05/ledger.json`). This excludes each subagent's harness overhead.
- The harness listed each draft subagent at 66,623 to 70,512 tokens in all (total 477,944 for the 7; read from the task notices, not from a stored file).
- Worker steps behind the drafts: the 20 source runs took 102 steps and 259,859 tokens in / 2,911 out (T04 `ledger.json`); that cost was already spent in T04, not in this run.

## What the loader and lint say

`load_skills(packages/skills/skills)` loads 0 and refuses all 7 as `unreviewed` ("the lock file has no reviewed entry"). `python -m skills.lint` exits 1 with 7 `not-pinned` problems. Both are expected: a draft has no lock entry until the owner reviews and pins it (T06). No draft failed the format check.

## Things the owner will see in review

- The two archetypes are coarse labels. The `font-size` runs' tickets name other properties too (for example `height on .ops-timeline-handle`, `border-radius on .ops-rules-alarm`), so those drafts talk about height, gap, border-radius. They describe the tickets, not only font size.
- The 7 drafts overlap a lot (same fix shape: find the rule, restore the stated value). Haiku had no view of the other groups, so the names differ but the content repeats. T06 will probably merge them into a few skills.
- The body steps were not checked against a run. Some (for example "decide by specificity", "ast_grep on an inline style") go beyond what the 20 runs did. That is for the review.
- Calls are not metered by a ledger (none exists for Claude sessions).
