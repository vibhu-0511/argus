## Choices I made (not measured, change them if you disagree)

- **`repro: false` in both configs.** The question is single fix agent vs planner plus subagents. The repro stage is the same in both variants, needs the Docker rig, and the one P5 dry run found no valid repro in three tries on a CSS-mutation bug (docs/notes/p5-t14.md). With it off the fix prompt says `Repro: not-run` for both.
- **Planner context is empty** (`Repo context: none`). Set `params.context` in `B.agent.json` to give it a short description of the repo; do it before the run, not after seeing results.
- **Caps:** `step_cap` 20, `token_cap` 150000 per bug (for B the planner's tokens come off it and the rest is split among the subagents), `context_budget` 12000 with the `cap` strategy, sized for a 16k-token window on the local model. These are guesses.
- Run A first, then B, not at the same time: one Ollama server on one CPU, and timing would be mixed.

## Limits to state wherever the numbers are quoted

- `gemma4:e4b` is a small local model. It is not the production model, so the result says nothing about how the variants compare on a strong model. The P8-T01 notes name coding with shared context as a bad fit for multi-agent (docs/notes/p8-t01-multi-agent-notes.md), so a loss for B here is an expected outcome, not a harness fault.
- One run per task per variant, 20 tasks: wide intervals, no repeat for noise (P5 measured run-to-run noise separately, `scripts/run_noise.py`).
- Subagents run one after the other in one worktree (ponytail ceiling in `planner.py`), so B is not the parallel design the multi-agent post describes.
- Latency is wall clock on one CPU machine with Ollama, with `repro` off.
