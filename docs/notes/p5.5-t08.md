# P5.5-T08 ablation: with skills vs without skills (held-out set)

Written on 2026-11-02 **before any run**, and filled in after. Sections "Cost estimate" and "Design" are what was decided up front; "Results" comes at the end.

## The set is 29 tasks, not 30

The task row says "the same 30 tasks". The held-out set is the 30 seeded tasks in `packages/skills/split.json`, and 29 of them run: `bug-17` no longer applies to platform HEAD (same as P5-T14). Both rows use the same 29. The criterion's "30" is not met literally; it is met on the 29 that can run.

## Cost estimate

From P5-T14 (`docs/notes/p5-t14-results.md`) and the stored variant A runs:

- Variant A stored: 29 runs, 228 fix-stage worker steps (7.9 per run) and 83 repro-stage steps, 311 in all. Fix-stage tokens per bug (chars/4) are 37,419 in and 205 out.
- P5.5-T04 (`docs/notes/p5.5-t04.md`): fix-only runs on easy mutants took 5.2 steps per run on average.
- Row 1 (skills on, fix stage only, sonnet): 29 runs. A skill load adds one step (`load_skill`) in a run that loads, so I expect **about 8 to 10 worker steps per run, 230 to 290 in all** (planning figure 260). No repro turns.
- Tokens (chars/4 estimate of the messages): about 29 x 40,000 = **1.2 million in, 6,000 out**. A loaded skill body is at most 8,000 characters (2,000 tokens) and sits in every later message of that run, so a run that loads one adds up to about 2,000 tokens per later step.
- Harness tokens per worker step are not visible. With the P5-T14 guess of about 70,000 per step, 260 steps is **about 18 million harness tokens**, all on sonnet. This is a guess, not a measurement. Plus about 10 coordinator sessions' worth of overhead (T04: about 70,000 to 80,000 each, 29 coordinators if one per run, fewer if each takes several runs).
- Row 2: nothing, if the stored runs are valid (below).
- Limits: at most 3 coordinators at once (two other sessions use the machine and Docker).

The owner approved wave 5 including this run (stated in the task).

## Design

### Row 2 (without skills): reuse the stored P5-T14 variant A runs

The stored runs are `packages/eval/results/t14/A/<task>/` (29 runs, sonnet on every stage, no router, one run per task). They are valid for this comparison. What I checked:

1. **Loop code.** `git diff 1cba1a0 HEAD` (1cba1a0 is the commit the A runs recorded as `git_commit`) over `packages/fix-loop/src`, `packages/repro-agent`, `packages/argus-core/src`, `packages/bench` and `packages/eval/policies` touches only: `fix_loop/loop.py` (the `skills=` argument and the policy-event logging), `fix_loop/sandbox.py` (a warning log when a container call fails; the docker command is unchanged), `fix_loop/skills.py` (new), `argus_core/trace_normalize.py` (span names, not the loop) and a new policy file. With `skills=None` the new loop code takes the old path.
2. **Byte comparison, run once, kept as `packages/eval/swarm/cmp_old_loop.py`.** It loads `loop.py` from commit 1cba1a0 and today's `loop.py` (with `skills=None`), feeds both the same scripted replies (search, read_file, an unknown `load_skill`, submit), and compares every message the model would see and every trajectory step. Output: `messages identical: True | steps identical: True | stop: submit submit | turns: 4`. The system message is `AGENTS.md` plus the protocol text; the blob of `packages/fix-loop/AGENTS.md` is the same at 1cba1a0 and at HEAD (`ab50374f...`), and `prompt.py` and `turn.py` are unchanged.
3. **User message.** All 29 stored A runs have `repro_found: false`, so their fix prompt said `Repro: not-run`. I rebuilt `Ticket:\n<text>\n\nRepro: not-run\nLocate: none\n` from each seeded ticket and hashed it: **29 of 29 equal the `prompt_hash` stored in that run's trajectory**. So the fix stage of A ran on exactly the input that a fix-only run gets.
4. **Tasks.** `git diff` shows `packages/bench` (tasks, bug patches, scorer) unchanged since 1cba1a0. The platform checkout's HEAD commit is dated 2026-10-14, before the A runs.

What is **not** identical and is said plainly: (a) the A runs also spent 83 repro-stage steps that did not reach the fix prompt, so I compare the **fix stage only** in both rows (tokens, steps, dollars); (b) one run per task per row, so a different model draw is the main noise, not a difference in inputs; (c) the A runs were made on 2026-11-01 and row 1 on 2026-11-02 or later, on a machine shared with other sessions, so latency is not comparable and I do not read it; (d) `A-seed-h06` and `A-seed-h09` were excluded by the scorer (exit 2) in P5-T14; they stay excluded in row 2 and a row 1 run of the same task is left out of the paired comparison if the other one is excluded.

### Row 1 (with skills): new variant S

Variant S in `eval.t14_turn` (run id `S-<task id>`, runs under `packages/eval/runs/p55-t08/<task id>`, git-ignored): the seeded task, the same strong-only policy as A (sonnet, no router), the same strategy `cap`, budget 32,000, step cap 20, and the same fix prompt as A, with `run_fix(..., skills=packages/skills/skills)`. The repro stage is off, as in variant T: A's repro stage found nothing in 29 of 29 runs, so A's fix prompt was `Repro: not-run` throughout (point 3 above), and running it again would only add 3 pointless steps per run, rig load and the replay hazard of P5-T14. The only difference between the rows is therefore the skills catalog in the system message and the `load_skill` tool. A test (`test_variant_s_runs_a_seeded_task_fix_stage_only_with_the_skill_catalog`) checks the first turn is a fix turn, the prompt says `Repro: not-run` and the catalog is there.

The skills are the 5 reviewed and pinned ones from T06, drawn only from train mutants (`split.json` check). The held-out set is not touched.

Tokens are chars/4 estimates, cached 0, as in P5-T14.

### Skills loaded (counted by `loaded_names` on the stored trajectories)

- 14 of 29 runs loaded a skill, one each; 15 loaded none. `css-value-changed-in-existing-rule` was loaded in 12 runs, `css-rule-missing-for-class` in 2. The other 3 skills (`svg-transform-box-missing`, `css-property-missing-from-grouped-rule`, `css-custom-property-missing-from-base-rule`) were loaded in no run, so the two thin skills got no evidence either way.
- With a skill loaded: 14 scored runs, 10 resolved. No skill loaded: 15 scored runs, 11 resolved. A loaded skill is not linked to a better result here (and loading is the model's choice, so this is not a controlled split).
- The allowlist (a loaded skill narrows the tools) blocked a call twice in all 227 steps (`not-allowed` in `seed-e01` and `seed-m07`).
- The per-task list of which skill each run loaded is in `report.txt`.

### Reading

- **Skills did not help on this held-out set.** Resolve rate: no difference seen (every one of the 27 paired tasks has the same outcome; the intervals overlap almost completely). Tokens: a bit higher (+8%). Steps: unchanged. I did not touch the skills.
- A possible reason, not tested: the 5 skills came from train mutants of two easy archetypes (font-size and missing-style; `docs/notes/p5.5-t04.md`). The tasks A already solves are easy for this model with or without a playbook, and the 8 tasks nobody solved are probably not the shape the skills cover.
- One run per cell. The test cannot see a small effect either way. A fair statement: skills cost a little and gained nothing measurable at this size.

### What went wrong, and what was done

- **Scorer exit 2 on the first finished runs.** `seed-e01`, `seed-e02` and `seed-m01` ended with `verdict: excluded`. The cause was the environment, not the model: this worktree had no `packages/bench/node_modules`, so the scorer's `run-checks.ts` could not import `@playwright/test` (`ERR_MODULE_NOT_FOUND`, found by running the scorer by hand on a pending tree). I added a junction from the worktree's `packages/bench/node_modules` to the main checkout's copy (git-ignored, not committed), checked that the scorer then returned a real verdict, moved the three runs to `packages/eval/runs/p55-t08/_aborted/<task>-noscore/` (copies in `packages/eval/results/t08/_aborted/`; 21 worker steps, 92,294 tokens in) and ran those three tasks again from scratch with a fresh worker per step. Their first answers are not in the results. All 29 stored verdicts are `resolved` or `unresolved`; none is `excluded`. The same missing module may explain `seed-h06` and `seed-h09` being excluded in P5-T14; I did not check.
- No replay mismatch, no stalled run, no run reset.

### Cost (from the stored files)

- Tokens (chars/4 estimates of the messages, fix stage): 1,165,764 in and 5,831 out in the 29 stored runs (estimate was 1.2 million in); 92,294 in and 517 out in the archived ones.

Worker subagent token use is not visible here; at the P5-T14 guess of about 70,000 per step, 248 steps would be about 17 million, a guess.
- Row 2 cost nothing (stored runs).
