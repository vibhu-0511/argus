Draft pull request description for the P5.5 branch (`stack/p5.5-skills`). Base: the P5 branch or `main` once PR #11 is merged. Not opened.

## Problem

The fix loop starts every bug from nothing. Skills are a way to hand it a short, reviewed playbook for a known bug type, loaded only when a ticket matches. Two things were unknown: whether skills made from past successful runs help on bugs they were not made from, and whether a skill, which is just text the agent obeys, can be used to take over the agent.

## Solution

- A train and held-out split with a script check: no shared task id and no shared (file, operator) pair. Held-out is the 30 seeded tasks (29 run); train is 40 generated mutants.
- A skill loader in the fix loop. The prompt lists only each skill's name and description; a `load_skill` tool returns one body. 20 skills add 880 estimated tokens against 23,280 for their bodies. At most 3 skills load per run.
- 20 resolved train runs collected with Claude sessions as the model, 7 drafts written by Haiku subagents, and 5 skills reviewed and pinned (3 backed by 11, 3 and 4 runs; 2 thin ones backed by 1 run each).
- Trust controls: the review flag and a SHA-256 pin live in `skills.lock.json`, not in the skill file; a skill that is unreviewed, changed after review, or asks for a tool outside the loop's tools is refused with a typed reason; a loaded skill can only narrow the tools. A CI lint (`skills-lint.yml`, no model) checks every skill file, the lock, description specificity and, with a checkout, the paths a skill names.
- Measured, with Claude sessions as the model: a selection test (7 of 10 tickets got the right skill, 3 misses) and a with-vs-without run on the 29 held-out tasks.
- Four break-it tests: a skill that edits the bench checks, one that sends data out, one whose description matches every ticket, one that names a moved file.
- ADR-018 (format and distillation criteria) and ADR-019 (trust model), a package README, and the phase report against P5.

## Results

| Run (29 held-out tasks, fix stage, Claude sessions as the model) | Resolved (95% interval) | Tokens/bug (in + out) | List-price $/bug |
|---|---|---|---|
| Without skills (stored P5-T14 variant A) | 19 of 27 (51.5% to 84.1%) | 37,624 | $0.0769 |
| With the 5 skills | 21 of 29 (54.3% to 85.3%) | 40,400 | $0.0824 |

- **Skills did not help.** On the 27 tasks scored in both rows the outcome is the same on every task (19 resolved in both, 8 in neither). The 2-task gap in the headline comes from two tasks the scorer could not score in the without row. Tokens in are about 8% higher with skills.
- A skill was loaded in 14 of 29 runs. Only 2 of the 5 skills were ever loaded (`css-value-changed-in-existing-rule` 12 times, `css-rule-missing-for-class` twice).
- One run per task per row, one day apart; a small gain or loss is invisible at this size. The held-out tasks the skills are about (9 tasks labelled `font-size` or `missing-style`) came out the same: 4 resolved and 5 not, in both rows.
- Selection: all 3 misses chose the same skill, because the ticket text cannot tell three of the CSS skills apart; wording cannot fix that.
- Break-its: the poisoned skills are refused by the loader or stopped by the sandbox; the always-matching skill is caught by the lint and by the cap; a stale skill misled one of two recorded runs for 2 steps, and the path lint catches it. Details: `docs/notes/p5.5-break-its.md`.
- Skills stay off by default. ADR-018 says what must be shown before that changes: a repeated run with a measured spread and a per-archetype table.

## Architecture

**HLD.** Resolved train runs go into a draft script; a person edits and pins the result; the loader checks the pin and the tools at the start of every run and shows only the catalog; the model loads one body when a ticket matches. The eval harness runs the loop with and without the skills folder and the same report tool as P5 compares them.

```
 split ──> collect train runs ──> draft ──> review + pin (skills.lock.json) ──> 5 skills
                                                                                    │
 ticket ──> run_fix ──> catalog in prompt ──> load_skill ──> body in context <──────┘
                │            (trust checks at load, tool allowlist per call)
                └──> trajectory ──> loaded_names ──> eval.skills_ablation ──> phase report
```

The full diagram, with the P5.5 part marked, is `docs/architecture/overview.md`.

**LLD.**

| Piece | Where | Does |
|---|---|---|
| `skills.split` | `packages/skills/src/skills/split.py` | builds and checks `split.json` |
| `skills.collect`, `skills.draft`, `skills.draft_claude` | same folder | store resolved runs; write unreviewed drafts (the script writes the frontmatter) |
| `fix_loop.skills` | `packages/fix-loop/src/fix_loop/skills.py` | parse, size limit, `trust_refusal`, `tool_denied`, `catalog`, `load_skill`, `loaded_names` |
| `skills.pin`, `skills.lock.json` | `packages/skills` | the owner's sign-off: review flag and content hash |
| `skills.lint` | `packages/skills/src/skills/lint.py`, `.github/workflows/skills-lint.yml` | the loader's checks plus description and path checks, in CI |
| `skills.selection` | `packages/skills` | catalog-only selection test |
| variant `S`, `eval.skills_ablation`, `replay(fix_only)` | `packages/eval` | run the held-out tasks with skills, read the stored runs, build the results files |
| break-it fixtures and tests | `packages/fix-loop/tests`, `packages/skills/tests` | poisoned, always-matching and stale skills |
