### What the script does, for each idle gap

1. `wait`: sleeps for the gap (default 1200 s, 20 minutes; Render's documented sleep is after 15 minutes without inbound traffic, [p6-t00-versions.md](p6-t00-versions.md)), or with `--confirm` waits for you to press Enter once the Render dashboard shows the service suspended.
2. Sends one `POST <url>/webhook` with `X-GitHub-Event: ping`, a fresh `X-GitHub-Delivery`, `Content-Type: application/json` and `X-Hub-Signature-256` computed from `GITHUB_WEBHOOK_SECRET` over the exact body. Records HTTP status and seconds until the answer (client timeout 90 s, longer than Render's documented "about one minute").
3. Sends a second ping at once: the warm baseline.

Verdict of the cold ping against GitHub's 10 s delivery limit: `ok` = 202 in under 10 s; `slow` = 202 in 10 s or more; `error` = any other status (including Render's own 5xx while the instance starts); `no-answer` = connection error or the 90 s client timeout. The summary lists the idle gaps whose cold ping was not `ok`.

A `ping` has no issue or pull-request number, so the handler answers 202 `{"status":"ignored"}` without enqueuing anything ([webhook.py](../../packages/flow/src/flow/webhook.py), `ticket_id_of`). What is timed is Render waking the web service and the app answering, not Neon and not DBOS: the app opens its port before the engine starts ([p6-t12.md](p6-t12.md), "How the service starts"). A real issue event is also answered 202 before its enqueue runs, but its background enqueue then waits up to 120 s for the engine; that is the poller's case (T23), not this number.

## Owner steps

You need the Render service from T12 running. You do **not** need the GitHub webhook registered for this: the script sends the ping itself.

1. **Deploy the service** with [p6-t12.md](p6-t12.md) owner steps 1 to 6 (Neon, Render account, Blueprint, variables). Wait until `https://<your-service>.onrender.com/health` answers `{"status":"ok","engine":"ready"}`. Note the exact URL; I do not know the name Render will give.
2. **Set the two variables in the shell you will run the script from.** The secret must be the same string you gave Render as `GITHUB_WEBHOOK_SECRET`. In bash, without echoing it:

   ```bash
   read -s GITHUB_WEBHOOK_SECRET; export GITHUB_WEBHOOK_SECRET
   export ARGUS_FLOW_SERVICE_URL=https://<your-service>.onrender.com
   ```

3. **Do not touch the service for the first gap.** The first request after a deploy is not a sleep test: leave the service alone, send nothing else to it (no browser tab on `/health`, no uptime monitor), and let the script's first wait pass.
4. **Run it.** From the repo root, on a machine that stays awake for the whole run. The command below waits 11,400 s in total, 3 hours 10 minutes (five 20-minute gaps, then a 30-minute and a 60-minute gap). Drop the last two numbers for a shorter run of 1 hour 40 minutes:

   ```bash
   uv run --all-packages python packages/flow/scripts/p6_t13_cold_start.py --gaps 1200,1200,1200,1200,1200,1800,3600
   ```

   Or, to decide for yourself when the service is asleep, add `--confirm` (it then asks before each try instead of sleeping). Look in the Render dashboard for the service's state and events (the console wording is from memory, not seen).
5. **Read the output.** It prints one line per try, a markdown table, the summary, and writes `packages/flow/results/p6-t13/results.json` (raw timings per try: gap, start time, cold status and seconds, warm status and seconds, verdict).
6. **Sanity check the table.** A cold ping that answers in well under a second means the service was still awake (the gap was too short or something else sent it traffic). Say so in the note instead of keeping the row as a cold start.
7. **Copy back** to `docs/notes/p6-render.md` (create it): the date and time, the table the script printed, the list of gaps over 10 s (`gaps_over_10s` in the summary), the Render region and instance type as shown in the dashboard, and the commit of the repository you deployed. Commit `results.json` next to it. Only then may P6-T13 be ticked in `TASKS.md`: the acceptance is a table of cold-start times over repeated idle gaps that states which gaps exceed 10 s.

## What the result feeds

- P6-T16 (ADR-021) uses it as the evidence for treating webhooks as hints. If the cold ping is `slow` or `no-answer`, GitHub's delivery for the first event after a sleep fails, which is the premise of the poller.
- P6-T23 (Render sleeps and drops a webhook) is run for real against the same service.

## Not verified

- Everything above about Render's behaviour (sleep after 15 minutes, a cold start of about one minute) is the vendor's own wording read on 2026-11-01 ([p6-t00-versions.md](p6-t00-versions.md)), not something I measured.
- Whether Render holds a request while the instance starts or answers it with an error: unknown; the script records whatever it gets.
- Whether the Render health check (`/health`, set in `render.yaml`) counts as inbound traffic and keeps the instance awake: not stated in the pages read. If every cold ping is fast, this is the first thing to suspect; the dashboard's service events would show it.
- The 10 s limit is the figure in the phase file; I did not re-read GitHub's documentation for it today.
