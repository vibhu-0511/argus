## 1. What the code polls, and how it may keep Neon awake

`uv run --all-packages python packages/flow/scripts/p6_t14_neon_usage.py expected` computes this from the code, not from a guess (counts are wake-ups that each run at least one statement):

| Source | Setting (where) | Per hour while the process runs |
|---|---|---|
| Reconciliation poller | `PollConfig.interval_s = 300.0`, 30 tickets x 3 pages at most ([reconcile.py](../../packages/flow/src/flow/reconcile.py)); `ARGUS_FLOW_POLL_INTERVAL_S` overrides, floor 60 s | 12 polls. Each ticket listed costs one `DBOS.get_workflow_status` (`DbosLookup`), so at most 12 x 90 = 1,080 lookups. 0 tickets listed = 0 database calls from the poller. The GitHub list call is not a database call |
| `wait_for_database` ([db_wake.py](../../packages/flow/src/flow/db_wake.py)) | one probe connection, `select 1` | 1 new connection per enqueue (webhook or poller starting a workflow), none in steady state. `ATTEMPTS = 6`, backoff 1 s doubling to 15 s, only while the database does not answer |
| DBOS queue worker, queue `argus-flow` | `DEFAULT_QUEUE_POLLING_INTERVAL_SEC = 1.0` (`dbos/_queue.py`) | 3,600 dequeue attempts |
| DBOS queue manager | `check_interval = 1.0`, runs `list_queues()` (a SELECT) | 3,600 |
| DBOS background jobs | `_BACKGROUND_JOBS_INTERVAL_SEC = 1.0`, advisory lock plus delayed-workflow and timeout sweeps (`dbos/_workflow_commands.py`) | 3,600 |
| DBOS schedule poller | `scheduler_polling_interval_sec` default 30 s, 1 s for the first 60 s (`dbos/_dbos.py`, `_scheduler.py`) | 120 |
| DBOS notification poller | `use_listen_notify = False` in [config.py](../../packages/flow/src/flow/config.py), `notification_listener_polling_interval_sec` 1.0 s | one SELECT per second per workflow waiting in `recv` (the QA wait), none with no waiting workflow |

DBOS values are read from the installed dbos 3.4.0 source (pinned in `packages/flow/pyproject.toml`); they are DBOS's, not ours, and a DBOS upgrade can change them. DBOS also starts its own internal queue, which I did not count.

**How this can keep Neon awake.** Neon's Free compute suspends after 5 minutes without activity and "cannot disable" this (plans page, 2026-11-02). Two separate effects, kept apart:

1. **The poller alone.** An interval of 300 s is exactly the idle timeout, and each poll takes some seconds, so the gap between database activity is a little under 5 minutes: on paper the compute never reaches its idle timeout. Any interval above 300 s would let it suspend between polls, but each poll then wakes it and it stays up another 5 minutes, so the compute is awake about (5 minutes + poll time) in every interval. With an empty poll (no tickets) the poller makes no database call at all.
2. **DBOS itself, which matters more.** The wake-ups above occur about every second whether or not there is a ticket and whatever the poll interval. As long as the process runs, the longest gap between them is about 1 s, 300 times shorter than the idle timeout. So **by the code, Neon cannot scale to zero while the Render process is running, at any poll interval.** Raising the poller's interval does not change this. Only the process not running does: Render sleeping (15 minutes without inbound traffic, [p6-t00-versions.md](p6-t00-versions.md)) stops all of it, and Neon then suspends 5 minutes after the last query. Expected awake time is therefore about Render's awake time plus 5 minutes per wake. Raising `polling_interval_sec` of the queue (a `Queue` argument, `dbos/_queue.py`) would not be enough alone: the queue manager and the background jobs run every 1 s from constants and no configuration key was found for them.

This is a prediction from code, not a measurement. T14's 48-hour run is what decides it.

### Local probe (really run, not Neon)

`p6_t14_neon_usage.py idle-probe` launches DBOS exactly as `flow.dbos_runtime.launch` does (pinned version and executor id, queue `argus-flow`), enqueues nothing, and reads `pg_stat_database` commits plus rollbacks before and after a window. Run on 2026-11-01 19:56 UTC (the machine's clock), Windows, Python 3.12, dbos 3.4.0, `postgres:16` in a throwaway Docker container `argus-p6-t14-pg` on port 55437 (removed afterwards), 70 s warm-up then 120.0 s measured:

| Measure | Value |
|---|---|
| Transactions with DBOS idle | 1,673 in 120.0 s = **13.94 per second** (about 50,000 per hour) |
| Transactions with no DBOS (10 s before launch) | 3 |
| Connections open to the database during the idle window | 5 |

One run, one machine. It shows that an idle DBOS process commits many times a second, more than the lower bound of the table (which counts wake-ups, not statements). It does not show anything about Neon's idle detection, its wake-up time or CU-hours. Raw: `packages/flow/results/p6-t14/idle-probe-local.json`.

| Question | What the docs say | Page |

| API | `GET https://console.neon.tech/api/v2/consumption_history/v2/projects`, required `from`, `to`, `granularity` (`hourly` last 168 h, `daily` last 60 days, `monthly` last year), `org_id`, `metrics`; the compute metric is `compute_unit_seconds` (raw CU-seconds, converted CU-hours); bearer API key. | API on the Free plan | **Not available.** Plan availability column: "Launch, Scale, Agent, Enterprise"; 403 "This endpoint is not available for your plan" (checked) | same |

So on the Free plan the only documented source is the **Compute** figure in the project's Usage panel, a running total. There is no documented per-day figure on Free; per-day exists only through the API on a paid plan. The script therefore works on **readings the owner types in** (total at a time), which give CU-hours per interval by subtraction, and it also accepts a saved API answer (daily rows) if the owner is on a paid plan. Whether the Usage panel is shown on a Free project is not stated on the page; I assume yes, and the owner sees it on the first reading.

### Arithmetic, not a measurement

Only if the compute ran at 0.25 CU all the time (an assumption taken from the page's own example; the compute size on the owner's project is read in the Console, and the free plan autoscales up to 2 CU per the page): 0.25 x 24 = 6 CU-hours a day, 12 in 48 hours, 100 used up after 400 hours (the page's own figure), about 16.7 days. An always-awake service does not fit a 30-day month under that assumption (180 CU-hours). That is what the 48-hour run must confirm or refute with a real figure.

## 4. Owner steps

I could not do any of these. The console wording is from memory except where section 2 says checked.

1. **Neon project and Render service.** [p6-t11.md](p6-t11.md) section 4 (project, direct URL with `sslmode=require`) and [p6-t12.md](p6-t12.md) owner steps 1 to 6. Note in the Console: the plan (Free), the **compute size** shown for the branch, and the date the billing period started if the Billing page shows it.
2. **Turn the poller on, with nothing to poll.** In Render set `ARGUS_FLOW_POLL_ENABLED` to `true`, `GITHUB_TOKEN` (read-only token from T12), and `ARGUS_FLOW_TICKET_LABEL` to a label that **no issue has** (for example `argus-t14-none`). Leave `ARGUS_FLOW_POLL_INTERVAL_S` unset (300 s). Reason: the Blueprint ships polling off because the GitHub write client is stubbed ([p6-t12.md](p6-t12.md), "What is stubbed"); with no label every open issue would start a workflow that fails. With a label nobody has, the poller lists no ticket, so it starts nothing and the run measures the polling loops, not tickets. Do **not** register the GitHub webhook for this run.
3. **Keep the service awake for the 48 hours.** Render sleeps after 15 minutes without inbound traffic and background polling does not count ([p6-t00-versions.md](p6-t00-versions.md)). Send `GET /health` (it does not touch the database) every 10 minutes from something that stays on, for example:

   ```bash
   while true; do curl -s -m 70 -o /dev/null https://<your-service>.onrender.com/health; sleep 600; done
   ```

   48 hours of an awake service is 48 of the 750 free instance hours. Do not use `/health/db`: it touches the database and would spoil the measurement. If your machine sleeps, the run is broken; write that in the note.
4. **Take readings** of the Compute figure (project, Overview, Usage panel) and write the time you read it, in UTC to the minute:
   - **R0** just before the first start of the service (the figure may be 0, or not if you already used the project);
   - one every 12 hours while the service runs (R1 to R3);
   - **R4** at 48 hours after R0 or later, **while the service is still running**;
   - **R5** at least 90 minutes after you stop the keep-alive, as a cross-check that the total stops growing. Write what the figure did.

   The panel "may be delayed by about an hour", so the split between neighbouring intervals is blurred by up to that long; the total from R0 to R4 understates the last hour. Also record, from the Console, any time the compute shows as suspended during the window (the Monitoring page is where I remember it from, not checked). One suspended period of hours during the run answers "did polling keep it awake" directly.
5. **Write the readings file** (anywhere; do not commit anything secret, there is none in it):

   ```json
   {"readings": [
     {"at": "2026-11-05T09:00:00Z", "cu_hours": <R0 Compute figure>},
     {"at": "2026-11-05T21:00:00Z", "cu_hours": <R1>},
     {"at": "2026-11-07T09:00:00Z", "cu_hours": <R4>}
   ]}
   ```

   The figures are the running total from the Usage panel, in CU-hours, within one billing period (the script refuses a total that falls). On a paid plan you may save the Consumption API answer instead (`granularity=daily`, `metrics=compute_unit_seconds`, one project); the script reads `compute_unit_seconds` from it.
6. **Run the comparison** (the compute size is what the Console showed, for example the number you read, not a default):

   ```bash
   uv run --all-packages python packages/flow/scripts/p6_t14_neon_usage.py compare --usage <readings.json> --cu <compute size in CU>
   ```

   It prints and writes `packages/flow/results/p6-t14/compare.json`: CU-hours and hours per interval, the total, `active_fraction` (CU-hours over the compute being on all the time; above 1 is possible if it autoscaled up), `reading` ("awake almost all the time" from a fraction of 0.9, a threshold I chose, the constant `AWAKE_THRESHOLD` in the script), share of the 100, and hours until 100 at that rate.
7. **Optional, 24 hours, a second run with no keep-alive.** Stop the loop of step 3, set nothing else, and read the Compute figure before and after. This is the natural behaviour (Render asleep, Neon asleep); it shows what the figure is when nobody calls the service. Not required by the task.
8. **Copy back** (to this file or `docs/notes/p6-neon.md`): the date and time of every reading, the compute size, the plan, the `compare.json` numbers, the suspended periods seen (or none), and one sentence "polling did / did not keep the database awake", based on `active_fraction` and the suspended periods. Commit `compare.json` and the readings file. Only then tick P6-T14 in `TASKS.md`. The acceptance also asks that the measured CU-hours are compared with 100 CU-hours/project: `share_of_allowance` is that comparison; the "per month" wording stays as recorded in section 3 unless you decide it.
