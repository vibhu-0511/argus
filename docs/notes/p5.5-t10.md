# P5.5-T10 skill trust controls

Code: `trust_refusal`, `tool_denied`, `content_hash`, `read_lock` in `packages/fix-loop/src/fix_loop/skills.py`; the run-time check in `loop.py`; the owner's pin command `packages/skills/src/skills/pin.py`; the lock `packages/skills/skills.lock.json` (empty today: no skill is reviewed).

## The three controls

| Control | Where it lives | Checked | Typed reason |
|---|---|---|---|
| Review flag | lock entry `reviewed: true` (the frontmatter `argus-status` is a label only) | at load | `unreviewed` |
| Content-hash pin | lock entry `sha256` = SHA-256 of the whole SKILL.md, CRLF read as LF (`content_hash`) | at load | `not-pinned` (entry has no valid hash), `hash-mismatch` |
| Tool allowlist | the skill's own `allowed-tools` field, bare names from `fix_loop.tools.ALLOW` | at load, and at every tool call | `tool-not-allowed` |

Load-time order: unreviewed, not-pinned, hash-mismatch, tool-not-allowed. A refused skill is left out of the catalog and out of the `load_skill` enum, and the refusal is logged with the reason. Because the hash covers the frontmatter, a change to `allowed-tools` or to `argus-status` after review is a `hash-mismatch`.

## Choices where the T01 notes were open or I deviated (owner to confirm)

1. **A skill with no lock entry is `unreviewed`, not `not-pinned`.** T01 said both (a missing entry is unreviewed in the review row, `not-pinned` in the pin row). A draft from T05 has no entry, and "unreviewed" is the plain word for it. `not-pinned` is kept for an entry that says reviewed but has no valid `sha256`. The T12 lint should use the same split.
2. **A bad name in `allowed-tools` is `tool-not-allowed`, not `bad-frontmatter`** (T01 said `bad-frontmatter`). The T10 task wording is "a skill cannot request tools outside its allowlist", and the reason already existed for it. The format check (`_parse`) does not look at tool names.
3. **Run-time check** (`tool_denied`): once a skill is loaded, the agent may call only the tools every loaded skill allows (intersection with the loop's tools). A loaded skill with no `allowed-tools` gets the read-only set (`read_file list_dir search ast_grep`), as T01 recommended, so reviewed fix skills must list `edit`. **Two refinements to T01:** `submit` and `load_skill` always pass (a run must be able to end; without this a skill without `submit` would trap the run until the step cap). With no skill loaded there is no limit, so a run without a loaded skill is the same as before.
4. The run-time refusal is a `ToolError` with code `not-allowed` and a message starting `tool-not-allowed:`, because `ToolErrorCode` (and its JSON schema in `schemas/`) has no `tool-not-allowed` member; adding one means regenerating the schema. The stored step has `tool_error: "not-allowed"` and the message text carries the reason, which is what T13 and T14 can grep for.
5. A missing, unreadable, wrong-version or wrongly shaped lock gives an empty lock: every skill is refused as `unreviewed`, and the problem is logged at error level. It never trusts anything and never crashes a run.
6. `load_skills(directory, lock=None)`: the lock defaults to `skills.lock.json` in the parent of `directory`, which is `packages/skills/skills.lock.json` for `packages/skills/skills`.

## The owner's step

`uv run python -m skills.pin NAME --by YOUR-NAME` after reading and editing a draft. It writes the entry (`reviewed`, who, date, hash) and only if the loader would then accept the skill; otherwise the lock is left as it was and the reason is printed. Edit the skill again and the pin must be run again. No session ran it; there is no skill in `packages/skills/skills` yet.

## Limits

- The lock and the skill files sit in the same repo, so someone who can commit both can change both. The pin stops an edit that is not accompanied by the owner's lock change; code review of the lock diff is the control (ADR-019, T11).
- The allowlist narrows the loop's tools; it does not stop `run_cmd` when no skill is loaded, and it does not inspect what an allowed `edit` or `run_cmd` does (T13, T14 test that against the sandbox).
- The lint (T12) is separate and was not touched.
- Running tests here: `uv run pytest` fails on this machine (Application Control blocks the `pytest.exe` launcher) and a plain `uv run` does not install the workspace members; the commands in this note use `uv run --all-packages python -m pytest`.
