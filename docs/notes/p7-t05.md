# P7-T05 No-egress policy in every execution context

Status: **built and run locally; NOT ticked.** The acceptance text needs the same probe on a GitHub Actions run, and the branch is not pushed. Nothing here claims an Actions result.

## What the probe is

- Code: `packages/guard/src/guard/egress.py`. Command: `uv run --all-packages python -m guard.egress --context local --control --out packages/guard/results/egress-local.json`.
- It starts the sandbox through `fix_loop.sandbox.run` (the same function the fix loop uses: image `argus-fix-sandbox:p3`, `--network none`, 1 CPU, 512 MB, work and checks mounts), with a shell script as the command.
- Three checks, each `reached`, `connect-failed` or `tool-missing`:

| Check | Command inside the container | Target |
|---|---|---|
| tcp | `nc -w 3 1.1.1.1 443` | 1.1.1.1:443 |
| https | `wget --no-check-certificate https://1.1.1.1/` | 1.1.1.1, by IP so it does not depend on DNS |
| dns | `nslookup example.com` | the container's resolver; counts as reached when the resolver answers at all, even "no answer", because the query has left the box |

- `no_egress_held` is true only when all three are `connect-failed`. `tool-missing` or `no-output` is not a pass; exit code is 1.
- `--control` runs the same script on Docker's default network (container name `guard-egress-ctl-<random>`, removed afterwards). A probe that cannot see `reached` there proves nothing.
- The first version used `https://example.com`. The control showed `connect-failed` for it with the network on, because this machine's DNS could not resolve `example.com` for `wget` (the resolver answered `nslookup` with "no answer"). That would have been a false pass, so the check was changed to the IP and re-run.
