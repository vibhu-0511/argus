# P6-T20 CI job for the flow tests

Date: 2026-11-01. File: `.github/workflows/flow.yml`. Architecture: [docs/architecture/p6.md](../architecture/p6.md), section P6-T20.

**The workflow has not run on GitHub.** The acceptance "Workflow green" can only be seen after a push, so the task is left unticked in `TASKS.md`.

**Owner step (one line):** push the branch, open the Actions tab, expect the `flow` workflow green.

## What the workflow does

- Runs on `push` and `pull_request` when a file under `packages/flow/`, `packages/argus-core/`, `uv.lock`, the root `pyproject.toml` or the workflow file itself changes.
- One job on `ubuntu-latest` with a `postgres:16` service container. The health check is `pg_isready -U postgres -d argus_flow_test` (5 s interval, 10 retries), so the steps start only when the database accepts connections.
- The password is the literal `flow-ci-throwaway-not-a-secret`, set once in the workflow `env`. It protects a container that exists for the length of the job and is not reachable from outside the runner. It is not a repository credential. The tests get it through `ARGUS_FLOW_DATABASE_URL` (step `env`).
- Steps, same actions and pins as the other workflows (`actions/checkout@v4`, `astral-sh/setup-uv@v5` with Python 3.12): `uv sync --all-packages --locked`, then the state-transition, webhook and reconcile test files by name, then the whole `packages/flow/tests` suite.
- `permissions: contents: read`. No model call, no repository secret, no cloud account. `check_no_secrets.py` finds no marker in `flow.yml`.

## What runs in CI and what skips

With `ARGUS_FLOW_DATABASE_URL` set, every test that uses the database runs (DBOS workflow, QA wait, poller with the real workflow, reconnect by killing sessions). These skip on the runner, as they did in my local run: the stop/start tests (`ARGUS_FLOW_TEST_CONTAINER`, a Docker container the test stops and starts: `test_launch_wake.py`, `test_neon_suspend.py`, `test_suspend_break_it.py`, 4 tests) and the TLS test (needs a server with `ssl=on` and `?sslmode=require`, 1 test).

## Checked locally (not on GitHub)

Command, as CI runs it, against my own throwaway container (`argus-p6-pg-w4c`, `postgres:16.15-alpine`, port 55438 on 127.0.0.1, generated password, `pg_isready` waited for):

```bash
uv run --all-packages python -m pytest packages/flow/tests -q
```

| Run | Result |
|---|---|
| Named step, no database (`test_states.py`, `test_webhook.py`, `test_reconcile.py`) | 206 passed in 5.07 s |
| Whole package suite, with the database | **315 passed, 5 skipped in 84.34 s** (wall clock 1 m 27.6 s; `uv` start-up included) |

Two earlier tries of the whole suite did not give a clean result, and this is why it matters:

- Try 1: 284 passed, 4 skipped, **32 errors** in 291.8 s. The errors were `DatabaseUnavailable: database did not answer after 6 attempts (ConnectionTimeout)` from `flow.db_wake`, at a time when the Docker engine on this machine was answering `500` to `docker ps` (the P5 ablation shares it). I did not look into each of the 32 errors; the one error text I saw was that timeout.
- Try 2: stopped at 92 %. Docker Desktop restarted underneath it (my container exited with code 255; the other containers on the machine went down too). I stopped my own pytest processes, started my container again and ran the full suite a third time. That is the 315 passed line above.

So the suite passes when the database answers, and the tests that wait on the database fail with a timeout when it does not. A GitHub runner's service container has no Docker Desktop layer in front of it; that is a reason to expect fewer such failures, not a measurement.

Differences from the real job: Docker image `postgres:16.15-alpine` here against `postgres:16` on the runner; Windows with the already-synced `.venv` here against a fresh `uv sync --all-packages --locked` there. `uv lock --check` passes. Nothing about the runner, action versions or the service health check was run: the YAML parses (checked with PyYAML) and `check_no_secrets.py` finds no marker in `flow.yml`.

`python .github/workflows/check_no_secrets.py` as a whole exits 1 on this branch, for three files that were already in the branch and are not part of this task: `dashboard.yml`, `eval-gate.yml` and `golden.yml` each contain the text `secrets.` (in a comment, or a real `secrets.PLATFORM_REPO_TOKEN` in `golden.yml`). `flow.yml` is not on the list.
