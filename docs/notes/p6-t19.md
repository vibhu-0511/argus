# P6-T19 crash-recovery experiment

Date: 2026-11-01. dbos 3.4.0, Python 3.12.10, Windows 11, Postgres 16 in a throwaway Docker container (`argus-p6-pg-w4a`, port 55437). Architecture: [docs/architecture/p6.md](../architecture/p6.md), section P6-T19. Raw numbers: [`packages/flow/results/p6-t19/`](../../packages/flow/results/p6-t19/) (`results-A.json`, `results-B.json`). Every number below is read from those files by `report` (command at the end).

**Hypothesis (phase file):** a durable DBOS workflow completes every run after a crash with no duplicated side effect, while the same pipeline without durability loses runs or duplicates effects.

## What was run

One ticket pipeline, two variants, the same fakes and the same step order:

| | A: no durability | B: DBOS |
|---|---|---|
| Code | `ticket_workflow.__wrapped__(ticket)`: the body of the workflow called as a plain function. The five steps run as plain calls (DBOS runs a `@DBOS.step` function outside a workflow as a normal call, `dbos/_core.py`). Only `DBOS.recv` is replaced by polling a signal file. | `flow.dbos_runtime.launch` (pinned `application_version`, `executor_id`, as the service does), `enqueue`, `get_result` |
| Restart | what a plain function can do: run again from the start when the ticket is seen again | `launch` again; DBOS recovers the pending workflow. Nothing enqueues it a second time |

**The world is a file.** `flow.ledger_fakes` replaces the in-memory `flow.fakes` with runners and a GitHub client that append one row per call to a JSON-lines ledger (`seq`, `op`, `key`, `n` = call counter for that op and key, `made`) and read it to find what already exists. A killed process takes nothing with it. Find-before-act is identical for A and B (an effect is made only if no earlier row with the same op and key was `made`; a PR create after a PR exists raises, as GitHub's 422), so only durability differs.

**The kill is real.** A child process runs the pipeline and, at a kill point, prints `AT <point>` and waits. The harness then hard-kills the whole process tree from outside (`taskkill /F /T`, i.e. TerminateProcess; the venv `python.exe` on Windows is a launcher that starts the real interpreter, so killing only the parent would leave the work running) and starts a second process. 15 kill points, in pipeline order:

| Kill point | Where | Step result stored? |
|---|---|---|
| `repro:before`, `fix:before`, `verify:before` | the runner is called, nothing done yet (= the step before has finished and stored its result) | yes for the step before |
| `repro:effect`, `fix:effect`, `verify:effect` | the run exists in the ledger, the step has not returned | **no** |
| `open-pr:before` | `push_branch` entered (verify stored) | yes for verify |
| `open-pr:pushed`, `open-pr:pr-created`, `open-pr:effects-done` | after the push / after the draft PR / after the label, before `open_pr_step` returns | **no** |
| `qa:before-wait` | open-PR stored, `await_qa` entered | yes |
| `qa:waiting` | inside the wait. For B: the `DBOS.sleep` row that stores the deadline exists | yes |
| `finish:before` | QA approved, `finish_step` entered | yes |
| `finish:ready`, `finish:effects-done` | after `ready-pr` / after the `done` label, before `finish_step` returns | **no** |

For B the harness reads `dbos.operation_outputs` after the kill and stores which steps were stored (`stored_steps_at_kill`); it matches the table in every one of the 150 kills (e.g. `fix:effect`: `repro_step` only).

**Measured per kill:** reached `done` after the restart (completed); duplicate side effects = ledger rows with `made` beyond one per (op, key); repeated calls = ledger rows with `n` > 1 (a second call that found the effect is not a duplicate); recovery time = from spawning the second process to its `DONE` line, so it includes interpreter start, imports and, for B, the DBOS launch.

**N:** 10 kills per kill point, 15 points, so **150 kills per variant**, 300 in all. Per kill point N=10, so a per-point p95 is the maximum or next to it; the pooled p50 and p95 are over 150. No attempt was discarded (`discarded_attempts` is empty in both files). The QA signal was always there when the restarted process asked for it (sent when the restarted process starts, or earlier for the `finish:*` points).

## What the numbers say

- **The hypothesis is only half supported.** B completed 150 of 150 with 0 duplicates, as predicted. A also completed 150 of 150: it lost no run. A plain function that is started again when the ticket is seen again, against runners and a GitHub client that find before they act and a QA signal that persists (a review comment does), gets to `done`. What kept A's effects at one each is the find-before-act rule in the fakes, not durability; that rule is the same for both variants by design. So this experiment cannot claim "DBOS prevents duplicates"; it can claim what is below.
- **A's 20 duplicates are one case.** Killed at `finish:effects-done` (the `done` label set, `finish_step` not returned), the rerun from the start goes through `open_pr_step` again: its `set_label(awaiting-qa)` sees the current label is `done`, so it is a new effect and the issue goes back to `argus:awaiting-qa`; `finish_step` then sets `done` again. That is 2 effects made twice (labels `awaiting-qa` and `done`: ledger `label` 4 made rows against 2 expected), in 10 of 10 kills at that point and in none at the other 14. PR, branch, comments and ready-for-review stayed at one. It depends on the label rule of the fake (`set_label` is a state, "found" means "is already the current label"), which follows the T02 table (`set-label`: add `argus:<state>`, drop the others); the real client would move the label the same way. The cause is the rerun from the start; B resumes at `finish_step`, so `open_pr_step` does not run again.
- **What DBOS bought here is not re-doing work.** Mean repeated calls per kill: A 4.47, B 0.93. B repeated nothing at the 7 points where no step was running a side effect (`repro:before`, `fix:before`, `verify:before`, `open-pr:before`, `qa:before-wait`, `qa:waiting`, `finish:before`): the stored results were replayed. It repeated calls at exactly the 8 points that are before the step result is stored, and only the calls of the step that was running. In B's 80 kills at those 8 points the repeated calls were: `dispatch-repro` / `dispatch-fix` / `dispatch-verify` (1 each at `*:effect`), `push-branch` (1 at `open-pr:pushed`), `push-branch` + `find-pr` (2 at `open-pr:pr-created`), `push-branch` + `find-pr` + `comment` + `label` (4 at `open-pr:effects-done`), `ready-pr` (1 at `finish:ready`), `ready-pr` + `comment` + `label` (3 at `finish:effects-done`). This is the at-least-once case: **a second call to the same key is expected there and is asserted only there** (`kill_before_result_stored` in the JSON; the pytest subset asserts it for `fix:effect` and the absence of it for `fix:before`). In none of them did the second call make a new effect: DBOS re-ran the step, the fake found the effect.
- **The recovery time does not show an advantage for DBOS, and cannot with these fakes.** B's pooled p50 is higher (4.92 s against 3.03 s); the p95s are close (6.05 and 6.01 s). Part of B's extra time is very likely the DBOS launch (migration check, queue start, recovery) on top of the interpreter start both pay, but I did not separate it. The two variants were also not measured under the same load: they ran at different times while other sessions' Docker jobs were going, and A's own clean-run times (4.2 to 6.8 s) are above its recovery p50 (3.03 s), which a quiet-machine A could not do. So treat the seconds as "process start dominates", not as a cost of DBOS or of the plain function. The fakes return at once, so A's rerun costs no time here; with real runners a rerun from the start is the whole pipeline, or at least the wait for every run it finds. That cost was **not measured** and no number is given.
- **QA wait.** `qa:waiting` completed 10 of 10 for both. For B the deadline is stored (the `DBOS.sleep` row existed at the kill, checked by the harness); a restarted A starts a new deadline. This experiment never lets the deadline run out, so the difference is not measured.

## What this does not show

- **Fakes, not the real thing.** `ActionsRunner` (T04) and a real GitHub client were not used: T04 has never run on GitHub and there is no real GitHub write client yet (only the Protocol in `flow.workflow`). Find-before-act in the fakes follows the rule of the T02 table, not the behaviour of the GitHub API. A real `find` can be late (eventual consistency) or fail; that is T21's lookup-error case on the fake only.
- **Hard kill of a local process on Windows**, not a Render restart or OOM kill. The database stayed up; a crash with the database also gone is T24's case, not combined here.
- **No model, no cost.** See the dashes above.
- **One ticket, one worker.** No concurrent tickets, no second executor taking over. The restart uses the same executor id and the pinned application version; a changed version (so DBOS would not recover the old workflow) was not tried.
- **Recovery time is wall clock on a loaded machine** (ablation jobs and other sessions running), A and B at different times. Treat the seconds as "process start dominates", not as a DBOS cost.
- Infrastructure events that did not end up in the numbers: the first invocation (A and B in one command) finished A, then died at B's warm-up because Docker Desktop restarted and the container went down; its A results are `results-A.json` and B was run in a second invocation (`results-B.json`). An earlier B smoke run lost its first process to a Docker port-forward timeout; the harness now retries a first process that never reaches its kill point (3 attempts, all attempts kept in `discarded_attempts`) and none was needed in the recorded runs. Zero DB connection errors were logged by the restarted processes of B.
- One field was wrong in the first output: `every_effect_once` compared a dict that included read operations with a count of 0, so it was false for every run. The script is fixed and the field in both JSON files was recomputed from the stored `effects_made` (nothing else touched): A 140 of 150 true (the 10 label cases above), B 150 of 150.

## Run it

Throwaway Postgres (own container, generated password, keep it out of files and out of the repo):

```bash
PW=$(python -c "import secrets;print(secrets.token_urlsafe(18))")
docker run -d --name argus-p6-pg-w4a -e POSTGRES_PASSWORD="$PW" -e POSTGRES_DB=argus_p6_t19 -p 127.0.0.1:55437:5432 postgres:16-alpine
until docker exec argus-p6-pg-w4a pg_isready -U postgres; do sleep 2; done
export ARGUS_FLOW_DATABASE_URL="postgresql://postgres:$PW@127.0.0.1:55437/argus_p6_t19"
```

The full experiment (one command; each variant took well under an hour here, not timed exactly; `--variants A` needs no database):

```bash
uv run --all-packages python packages/flow/scripts/p6_t19_crash_recovery.py --repeats 10 --baseline 5
```

It writes `packages/flow/results/p6-t19/results.json` (the two files committed here are from two invocations, `--variants A,B` which finished A and died at B, and `--variants B --out .../results-B.json`; see above). Tables from the files:

```bash
uv run --all-packages python packages/flow/scripts/p6_t19_crash_recovery.py report packages/flow/results/p6-t19/results-A.json packages/flow/results/p6-t19/results-B.json
```

The fast subset (3 kill points, one repeat, about a minute; the two DBOS tests are skipped without the variable):

```bash
uv run --all-packages python -m pytest packages/flow/tests/test_crash_recovery.py -q
```

Remove the container when done: `docker rm -f argus-p6-pg-w4a`.
