# P6-T07 Reconciliation poller

Date: 2026-11-01. Architecture: [docs/architecture/p6.md](../architecture/p6.md), section P6-T07. Code: `packages/flow/src/flow/reconcile.py` (state mapping, `Reconciler`, `poll_once`, `poll_forever`) and `github_read.py` (read-only GitHub reader).

## What it does

GitHub is the source of truth; a webhook is a hint that can be lost. The poller rebuilds a ticket's state from GitHub alone and starts the workflow through the same `Enqueuer` as the webhook, so both meet on `SetWorkflowID(ticket_id)`.

Per ticket (`owner/repo#number`) the reader makes five GET requests: the issue (state, labels), the PRs with the stable branch as head (`state=all`), the branch ref, the `workflow_dispatch` runs (newest 100), the issue comments (first 100). It cannot write: there is no other HTTP verb in the module.

`derive_state(github_state) -> State` is pure. Strongest evidence first:

| GitHub shows | State |
|---|---|
| PR merged | `done` |
| PR closed, not merged | `rejected` |
| PR open and not draft (ready for review) | `done` |
| label `argus:done`, `argus:rejected`, `argus:timed-out` or `argus:failed`, or the matching comment marker | that state |
| the latest run of a step concluded with anything but `success` | `failed` |
| issue closed, none of the above | `rejected` (someone closed it before a PR existed) |
| draft PR open and label `argus:awaiting-qa` | `awaiting-qa` |
| a PR or the branch exists, otherwise | `opening-pr` |
| verify run succeeded (no PR yet) | `opening-pr` |
| fix run succeeded | `verifying` |
| repro run succeeded | `fixing` |
| any dispatch run exists | `reproducing` |
| nothing | `received` |

That is the "GitHub shows" column of `flow.states.STATES`. Choices that go past that column, so reviewable: a closed issue with nothing else is `rejected`; a non-draft open PR is `done` even if a human marked it ready; for the end states a comment marker counts like the label, because the workflow posts the comment before it sets the label and a lost step can leave only the comment; for `awaiting-qa` only the label counts (the table says a PR without the label is still `opening-pr`, and the replay of `open_pr_step` is harmless).

`Reconciler.reconcile(ticket_id)`:

1. Read GitHub. Any error (HTTP status, dropped connection) raises `GitHubReadError`; nothing was written, nothing enqueued.
2. Derive the state, ask the workflow store (`DbosLookup`: `DBOS.get_workflow_status(ticket_id)`).
3. Workflow exists: report `action="exists"` with its DBOS status and the state in its output; never enqueue again. `diverged` is true when a finished workflow ended in another state than GitHub shows now.
4. No workflow and the state is an end state: report `action="settled"`, start nothing (nothing left to run).
5. No workflow, state not terminal: `enqueue_reconcile(ticket_id)`, `action="started"`. The workflow then walks its steps; each step finds the run, branch and PR that GitHub already shows through its idempotency key (T03), so it lands at the derived state and opens no second PR. Tested: with a draft PR and finished runs seeded, `create_draft_pr` is never called and one PR exists.

`poll_once()` lists open issues (`state=open`, newest update first, pull requests skipped), reconciles each, and returns `PollResult(reconciled, errors)`. A failed listing raises. A failed ticket is reported in `errors` (type name, or the `GitHubReadError` text which has no token) and skipped; the others go on.

## How "sets the workflow to the right state" works, and what it does not do

The poller does not write a state into DBOS. There is no resume-at argument on the workflow (`workflow.py` is not touched by this task), and the workflow's state is what its stored steps replay. So "right state" means two things, both tested: `derive_state` returns the state GitHub shows, and a workflow started from that GitHub state reaches the end with the existing runs and PR reused. Not covered: resuming a workflow that already exists but is stuck (ERROR or CANCELLED keeps its id and is only reported; that is DBOS recovery and T19), and a deliberate re-run (attempt 2, reserved by T02).

## Poll defaults are a choice for ADR-021 / ADR-022 to confirm

| Setting | Env | Default | Bound |
|---|---|---|---|
| repository | `ARGUS_FLOW_REPO` | none, required | `owner/name` |
| ticket label | `ARGUS_FLOW_TICKET_LABEL` | unset: every open issue (the webhook also enqueues any issue) | |
| page size | `ARGUS_FLOW_POLL_PAGE_SIZE` | 30 | 1 to 100 (GitHub `per_page` maximum) |
| max pages | `ARGUS_FLOW_POLL_MAX_PAGES` | 3 | at least 1 |
| interval | `ARGUS_FLOW_POLL_INTERVAL_S` | 300 | at least 60 (a typo cannot hammer the API) |

These numbers are picked, not measured. No cost is claimed. What the ADRs still have to settle, with T13 and T14:

- GitHub request budget: one ticket costs 5 reads plus 1 listing request per page. Check `page_size * max_pages * 5` reads per interval against the rate limit of the token's account type on the ADR date.
- Neon: a DB read per ticket (`get_workflow_status`) every interval is activity; whether a 300 s interval keeps the compute awake, and what that costs in CU-hours, is T14's measurement. Neon's documented scale-to-zero is after 5 minutes of inactivity (`p6-t00-versions.md`).
- Render free: `poll_forever` runs inside the service, so it runs only while the service is awake. It cannot wake a sleeping instance; what wakes it (a webhook, an external ping, a scheduled GitHub Actions job) is for ADR-021/022 and T13/T23.
- Beyond `page_size * max_pages` open tickets the least recently updated ones are not polled.

## Wiring for later (not deployed)

```python
reader = HttpGitHubReader.from_env()                 # GITHUB_TOKEN
poller = Reconciler(reader, DbosLookup(), enqueuer, PollConfig.from_env())
# in the FastAPI lifespan, after flow.dbos_runtime.launch():
stop = asyncio.Event(); task = asyncio.create_task(poll_forever(poller, stop))
...; stop.set(); await task
```

Token: `GITHUB_TOKEN`, read-only use. A fine-grained token with read access to Issues, Pull requests, Actions and Contents is enough for these reads; I did not try a real token (see below). T04 may choose another env name for its dispatch token.

## Found while building (for the orchestrator)

- **PR events name the wrong ticket.** `flow.webhook.ticket_id_of` builds `owner/repo#number` from `payload["pull_request"]["number"]`, which is the PR number, not the issue number. The workflow id is the ticket id, so with the real `DbosEnqueuer` a PR event would start a second workflow keyed by the PR number. Its docstring says mapping a PR back to its ticket is the poller's job. The poller does not do that mapping: it raises `NotATicket` for a number that is a PR (the issue API marks it with `pull_request`) and skips PRs when listing, so it never starts a workflow for a PR. The fix belongs in the webhook (T06 code): either ignore `pull_request` events for enqueueing, or map the PR to its issue (the workflow's PR title is `Argus fix for <ticket_id>`, which is a fragile link). Not changed here.
- **Run matching depends on T04.** The reader matches a run to a step by `display_title == effect_key(ticket, "dispatch-<step>")`, which is what `flow.states.EFFECTS["dispatch"]` says T04 sets as `run-name`. If T04 names runs differently, `_latest_runs` in `github_read.py` is the one place to change.
