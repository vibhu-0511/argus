Source: `phases/P08-argus-app.md`. P8 packages Argus as a GitHub App. Each tenant runs a reusable workflow in their own repo, with per-tenant quota budgets, ticket intake, PR creation with evidence, a backport bot, and a single-agent vs planner ablation. P8 was started with P6 still open (draft PR #12) and with the dependency of `P8-T04` on `P6-T04` waived; see `docs/notes/p8-waves.md`.

## P8-T03 Installation flow and token minting

A tenant installs the App on a repo; GitHub tells the flow service; the service remembers which installation covers which repo and can mint a one-hour token for exactly that repo.

| Piece | Where | Reused or new |
|---|---|---|
| Webhook path: HMAC check, 202, record after the response | `flow.webhook.create_app(on_installation=...)` | reused path (ADR-021: no GitHub call, no wait); the two events are recorded, not enqueued |
| Store: installation id -> tenant id (account numeric id) -> repos; applied delivery ids | `flow.installations.InstallationStore`, three tables in the flow database | new; same Postgres as DBOS, no new service |
| Token for one repo | `flow.installations.mint_for_repo` -> `flow.app_token.AppTokenMinter` | `app_token` reused unchanged (explicit ADR-026 profile, one bare repo name, answer checked) |
| Env vars | `render.yaml`: `ARGUS_GITHUB_APP_ID`, `ARGUS_GITHUB_APP_PRIVATE_KEY`, both `sync: false` | `GITHUB_WEBHOOK_SECRET` already there |

How the criteria are met:

- **Token scoped to the installed repo.** `mint_for_repo(store, "owner/name", profile)` looks the repo up first. Only a hit leads to `AppTokenMinter(app_id, key, installation_id, repo)`, which posts `permissions` (a `PROFILES` entry) and `repositories: [name]`, then rejects any answer that is broader than asked. Test: the mock records the body and the token works on `acme/shop`.
- **A call on another repo fails.** Two ways, both tested: a repo not in the store (never installed, removed, installation deleted) raises `RepoNotInstalled` before the key is read and before any HTTP call (`api.calls == 0`); the token made for repo A used on repo B gets the mock's 404 (GitHub's answer for a repo the token cannot see).
- **Removal revokes.** `installation_repositories` / `removed` deletes the row, `installation` / `deleted` drops the installation and its repos. The next `mint_for_repo` raises. A token already minted lives out its hour; GitHub fixes that, not this code.
- **Redelivery changes nothing.** `X-GitHub-Delivery` is inserted into `argus_deliveries` in the same transaction as the change (`on conflict do nothing`). A repeat returns `False` and writes nothing, so a redelivered `created` also cannot undo a later `removed`. A write that fails rolls the delivery row back, so GitHub's retry still goes through. Events without a delivery id are idempotent by their upserts.
- **Fast answer.** The handler answers `{"status": "installation"}` with 202 and runs `apply` as a background task; a failing store is logged by exception class only (the URL has a password) and does not change the 202.
- **No secret in logs or errors.** `ScopedToken` repr hides the token (`InstallationToken` has `repr=False`), `InstallationStore` repr hides the URL; the test collects reprs, error texts and all log records, checks that the token, the JWT, the key body and the database password are absent, and that `argus_core.redact` leaves the text unchanged.
- **Tenant id for P8-T07.** `ScopedToken.tenant_id` and `InstallationStore.find(repo).tenant_id` are the installation account's numeric id as text. It survives a rename of the account (tested). The login is stored beside it for display.

Ceilings (marked `ponytail:` in the code): the store is as fresh as the events it received (a lost event leaves a stale row; stale rows fail safe); `suspend` and repo renames are ignored; no ordering between different deliveries. Nothing in the running service calls `mint_for_repo` yet (T04 and T08 do).

Not done: the real App and a real installation (owner steps in [p8-t03-owner-steps.md](../notes/p8-t03-owner-steps.md)); the `TASKS.md` box stays unticked.

Prove it (the store tests need a Postgres at `ARGUS_FLOW_DATABASE_URL`; without it they skip):

## P8-T11 Planner and subagents variant of the fix loop

One model call (the planner) turns the ticket plus repo context into 1 to 5 typed sub-tasks. Each sub-task then runs the existing single-agent loop (`run_fix`, P3-T06) as a subagent with its own message history and its own token and step cap. P8-T12 compares this variant with the single agent.

| Piece | Where | Reused or new |
|---|---|---|
| Loop each subagent runs | `fix_loop.loop.run_fix` (P3-T06) | reused, unchanged |
| Tier routing and quota accounting | `argus_core.router.Router`, `argus_core.ledger.Ledger` | reused, unchanged. The planner and the subagents use the same router or the same ledger and `complete` |
| Trajectory files | `argus_core.types.Trajectory`, `fix_loop.loop._write` | reused. The schema is unchanged |
| Plan types, `PlanError`, `run_planned`, `select` | `packages/fix-loop/src/fix_loop/planner.py` | new |
| Variant switch in the eval harness | `params.variant` in `eval.ablation._agent` (`single` is the default, `planner`) | 3 lines in `packages/eval` |

How the criteria are met:

- **The planner emits sub-tasks.** `Plan` is a pydantic model: 1 to 5 `SubTask(title, instructions)`, no extra fields. The planner uses the strong tier through the existing `fix` stage, so `routing.yaml` and the policies are untouched. A reply that is not valid (not JSON, no sub-tasks, more than 5, a missing or extra field) raises `PlanError(reason, raw)`. A reply wrapped in a code fence still parses. The planner's call is already in the ledger and in `planner/trajectory.jsonl` when `PlanError` is raised, so failed plans cost tokens in the table, not nothing.
- **Subagents have their own budget.** `token_cap` and `step_cap` are for the whole bug. The planner's tokens come off `token_cap` and the rest is split evenly, so each subagent gets its own cap and the sum over all agents stays near the single agent's cap. A subagent that hits its cap stops as `token-cap`; the next one still runs. The whole run ends early only on a quota refusal, because the shared ledger would refuse every later agent too. Each subagent builds its own messages, so one subagent never sees another's history. The worktree is shared, so a later subagent sees the earlier edits.
- **Tokens across all agents are in the ledger.** One `Ledger` instance, one `run_id`. Test: the ledger bucket (requests, charged tokens, cached) equals the sum over planner and subagents. The ledger has no run id field (it counts per model per day), so "same run id" means every agent's trajectory carries the same `run_id`, not that the ledger stores it.
- **Per-bug numbers for the T12 table.** `out_dir/trajectory.jsonl` holds every step of every agent in order (re-indexed), so a harness that reads one trajectory per bug sums all agents. `out_dir/agents.json` and `PlanResult.agents` give tokens in, out and cached and call count per agent; `PlanResult.subagent_calls` is the number of subagent model calls. Per-agent files: `planner/`, `sub-1/`, `sub-2/`.
- **Switchable.** `fix_loop.planner.select("single" | "planner")` returns `run_fix` or `run_planned` (same arguments; the planner variant also takes `context`). In the eval harness the agent config sets `params.variant`. Everything else in the config and the task list stays the same.

Stop reason of the planner variant: `submit` only when every subagent submitted; otherwise the first subagent reason that was not `submit`. A malformed plan is not a stop reason (the enum in `argus_core` and its committed schema are unchanged); it is the `PlanError` exception, and the T12 harness decides how to score it.

Ceilings (marked `ponytail:` in the code): subagents run one after the other in one worktree; the planner is one call with no retry. Upgrade path: one worktree per subagent plus a merge step, only if the ablation says the variant is worth it.

```bash
uv run --all-packages python -m pytest packages/eval/tests/test_ablation_run.py -q
```

## P8-T04 Reusable workflow that runs the agent job in the tenant's repo

- New components: `.github/workflows/argus-reusable.yml` (`on: workflow_call`), the five-line caller `packages/app/docs/tenant-workflow.yml`.
- Links to existing parts: the T04 commit ran `flow.agent_job` (P6-T04) once per step with `ARGUS_STEP`; P8-T06 replaced that with `argus_app.runner`, which wraps `flow.agent_job.main`. `agent-job.yml` is untouched. The pusher is the App installation token, `flow.app_token` `write` profile (ADR-026, amendment 2026-11-03).
- How it works: the tenant's workflow labels-triggers (`issues: labeled`, label `argus`) and calls the reusable one. The called job checks out the tenant repo and the Argus code (both without kept credentials), then runs repro, fix and verify as three steps; each writes `result.json`, `patch.diff`, `trajectory.jsonl` into `argus-out/<step>/` and the next step reads the one before as `upstream.txt`. Only the fix step holds the tenant's `ARGUS_MODEL_API_KEY`. The token is the tenant's, `contents: read`, and is set in no step's environment. Nothing in the file pushes.
- Gap, on purpose: the T04 commit still ran the P6 default steps, which refuse a live issue; P8-T06 closes that. A `pull_request` trigger limited to the workflow file makes a real run possible (verify only, on the fixture repo, no model, no secret).

## P8-T06 Target-agnostic runner

- New components: `argus_app.runner` (`python -m argus_app.runner`, plus `plan <repo or .argus.yml>` which starts nothing), `config/dcortex.argus.yml` (the dcortex repo from `config/platform.md` as a tenant config), the fixture repo `packages/app/tests/fixtures/second-repo`.
- What was hardcoded to dcortex and where it went: `flow.agent_job` default steps need `ARGUS_PLATFORM_REPO`, a seeded task directory, the Vite rig (`repro_agent.trees`: port 5297, `apps/canvas`) and the bench scorer, whose flow list is `argus_bench.mutate._FLOWS`. Those stay for the seeded-task benchmark and are untouched. The tenant runner reuses the harness (`flow.agent_job.main`: job from the environment, scrubbed failure reasons, `result.json` last, exit 0 or 1) and swaps the three steps for ones that read `.argus.yml` (T05): `start`, `test`, `routes`, `base_url` and `budget` (`max_steps` and `max_tokens` become the fix loop's `step_cap` and `token_cap`).
- The steps: **repro** starts the app, waits until every route answers (status below 400), runs the tests, and reports; it is ok when the app and routes came up, whatever the tests say (a failing test is the evidence). **fix** runs the P3 fix loop (`run_fix`) on a worktree with the ticket from the event payload (no GitHub token needed) and writes `patch.diff` (byte for byte, new files included). **verify** applies the patch in a fresh worktree and runs the same start, routes and tests; ok only if all hold. A target that is a folder of a bigger repo works (the worktree is of the git root, commands run in the same sub-folder).
- Safe by construction: the config is read once from the tree as checked out, so a patch that edits `.argus.yml` cannot change what verify runs (test). The tenant's own commands run with every secret-named variable removed from their environment, so the model key never reaches them (test). A start command that exits, a route that never answers, a missing `.argus.yml` or a missing field each end as a failure `result.json` with the reason (typed error text for the config cases), never a crash.
- Proof that no code changes between targets: `argus-app`'s test `test_the_runner_source_names_no_repo_command_port_or_route` checks the string literals of `runner.py`; the same code plans both configs (`plan`); and the fixture repo (flat Python package, stdlib server on its own port, `unittest`, a different layout from the dcortex pnpm monorepo) goes through repro, fix and verify for real (app started, routes fetched, tests run). The fix agent is a fake that edits the file (no model call); the repo has a typo committed on top by the test helper, and the run goes from `exited 1` to `exited 0`.
- Not done: **no run against the real dcortex repo** (no checkout used; its config is only loaded and planned, and its commands are from `config/platform.md` and `packages/fix-loop/AGENTS.md`, not checked), the real fix agent has never run on a runner or against a model, and a start command that starts containers is not stopped cleanly. Box unticked. Owner steps: [p8-t06-owner-steps.md](../notes/p8-t06-owner-steps.md).
- Proof: `uv run --all-packages python -m pytest packages/app/tests -q`, and `uv run --all-packages python -m argus_app.runner plan config/dcortex.argus.yml`.
