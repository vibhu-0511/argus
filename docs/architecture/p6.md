# P6 architecture

Source: `phases/P06-argus-flow.md`. P6 runs the ticket-to-fix pipeline as a durable workflow (DBOS), reached by a webhook that is only a hint, repaired by a reconciliation poller, executed on GitHub Actions, with a human QA signal wait. Deployed on Render free with Neon free Postgres. This file grows by one section per task. After each wave the orchestrating session folds the sections into the diagram in `overview.md`.

P6 was started before P5.5 and before P5 finished, on the owner's choice; see `docs/notes/p6-waves.md`.

## P6-T02 Workflow state machine

Components: `flow.states` (`State`, `Event`, `TRANSITIONS`, `next_state`, `STATES`, `EFFECTS` and the key functions `workflow_id`, `branch_name`, `effect_key`, `qa_signal_key`, `comment_marker`). Pure Python: no DBOS, no network, no clock, no randomness. Ten states (`received`, `reproducing`, `fixing`, `verifying`, `opening-pr`, `awaiting-qa`, and the terminals `done`, `failed`, `rejected`, `timed-out`), 12 legal transitions; any other (state, event) pair raises `IllegalTransition`.

Links to existing components: the step states name the repro agent (`repro_agent`), the fix loop (`fix_loop`) and verify (`verify`) as Actions runs, one `workflow_dispatch` run per step; nothing is imported. Used next by T03 (the DBOS workflow calls `next_state` and the keys), T04 (run title = `run_key`), T05/T06 (`workflow_id` is the workflow id both the webhook and the poller use), T07 (the "GitHub shows" column is what the poller reads), T08/T10 (`qa_signal_key`).

Files: `packages/flow/src/flow/states.py`, `packages/flow/tests/test_states.py`, `docs/notes/p6-state-machine.md` (tables generated from the code, checked by the test).

Proof: `uv run pytest packages/flow/tests -q`
