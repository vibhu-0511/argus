# P6 architecture

Source: `phases/P06-argus-flow.md`. P6 runs the ticket-to-fix pipeline as a durable workflow (DBOS), reached by a webhook that is only a hint, repaired by a reconciliation poller, executed on GitHub Actions, with a human QA signal wait. Deployed on Render free with Neon free Postgres. This file grows by one section per task. After each wave the orchestrating session folds the sections into the diagram in `overview.md`.

P6 was started before P5.5 and before P5 finished, on the owner's choice; see `docs/notes/p6-waves.md`.

## P6-T05 Webhook endpoint with HMAC verification

- **Component:** `POST /webhook` in a FastAPI app (`create_app()`), the entry point GitHub calls. It checks `X-Hub-Signature-256` (HMAC-SHA256 over the raw body) before anything else is read from the body.
- **Secret:** the environment variable `GITHUB_WEBHOOK_SECRET`, read on each request; never stored in a file or logged. Compare is `hmac.compare_digest`. Valid -> 202; invalid, missing or malformed header -> 401; no secret or an empty one -> 401 for every request (fail closed).
- **Links:** GitHub (sender) -> this endpoint. T06 adds the hint handling behind the same check; T12 deploys the app on Render.
- **Files:** `packages/flow/src/flow/webhook.py`, `packages/flow/tests/test_webhook.py`.
- **Proof:** `uv run pytest packages/flow/tests -q`

## P6-T06 Webhook as a hint: enqueue and return 202

- **Components:** the `/webhook` handler (after the T05 signature check) reads `X-GitHub-Event` and `X-GitHub-Delivery`, derives the ticket id `owner/repo#number` from the payload's `issue` or `pull_request`, schedules `enqueue_reconcile(ticket_id)` as a background task and returns 202. It reads nothing from GitHub. An event with no issue or PR number (ping, push, workflow_run) is acknowledged as `ignored` and not enqueued; the poller covers it. A signed body that is not JSON gets 400.
- **New seam:** `Enqueuer` Protocol in `flow/enqueue.py`, with `FakeEnqueuer` (tests) and `HintDedup` (bounded in-memory set of delivery ids, per process). The real DBOS implementation arrives in T03 and starts the workflow under `SetWorkflowID(ticket_id)`; T07's poller makes the same call, so webhook and poller share one workflow id per ticket. The delivery id is never a workflow key. A failed enqueue forgets the delivery id so GitHub's redelivery is not dropped.
- **Links:** T05 (signature check) -> handler -> `Enqueuer` -> T03 workflow; T07 poller -> same `Enqueuer`.
- **Files:** `packages/flow/src/flow/enqueue.py`, `packages/flow/src/flow/webhook.py`, `packages/flow/tests/test_webhook.py`.
- **Measured handler time:** a test drives the app as an ASGI server with a fake enqueue that sleeps 2 s. The response was fully sent after 0.8 to 1.8 ms (4 runs on this machine, in-process, no real network); the app returned after about 2.0 s because the enqueue ran after the response. This is the handler only, not a Render cold start (that is T13).
- **Proof:** `uv run pytest packages/flow/tests -q -s` (the `-s` shows the timing line)

## P6-T03 DBOS durable workflow on a local Postgres

- **Components:** `ticket_workflow` in `flow/workflow.py`, a DBOS workflow with five DBOS steps (`repro_step`, `fix_step`, `verify_step`, `open_pr_step`, `finish_step`). The body only orders the steps; every state move goes through `next_state` from [`flow/states.py`](../../packages/flow/src/flow/states.py), so an illegal move raises `IllegalTransition`. Each effect uses the keys in `states.py` (`effect_key`, `branch_name`). Step results are stored in the DBOS system database. The runners (repro, fix, verify) and the GitHub client are injected interfaces (`Runner`, `GitHubClient`) with fakes in `flow/fakes.py`; the real Actions dispatch is T04. Open-PR is find-or-create on one stable branch, draft, no `closes #N`, and a lookup error raises and creates nothing. After `awaiting-qa` a marked stub approves at once (T08 replaces it).
- **Real `Enqueuer`:** `DbosEnqueuer` in `flow/dbos_runtime.py` implements the Protocol in [`flow/enqueue.py`](../../packages/flow/src/flow/enqueue.py) that the webhook ([`flow/webhook.py`](../../packages/flow/src/flow/webhook.py)) and, later, the poller (T07) call. It enqueues under `SetWorkflowID(ticket_id)`; verified on dbos 3.4.0 that this works on a queue and that a second enqueue returns the first run, also after it finished.
- **Config decided before the first migration:** `flow/config.py`. `use_listen_notify=False`, `application_version="argus-flow-1"`, `executor_id="argus-flow-0"`, no conductor key; the database URL is read from `ARGUS_FLOW_DATABASE_URL`. Reasons and the T11 hand-off are in [docs/notes/p6-t03.md](../notes/p6-t03.md).
- **Links:** webhook/poller -> `DbosEnqueuer` -> queue `argus-flow` -> `ticket_workflow` -> steps -> runners and GitHub client. New dependency: `dbos==3.4.0` (brings `psycopg`); `uv.lock` updated.
- **Files:** `packages/flow/src/flow/workflow.py`, `dbos_runtime.py`, `config.py`, `fakes.py`; `packages/flow/tests/test_workflow.py` (needs Postgres, marker `postgres`), `test_config.py`.
- **Proof:** start a Postgres, set `ARGUS_FLOW_DATABASE_URL`, then `uv run python -m pytest packages/flow/tests -q` (exact commands in the note). Without the variable the 8 workflow tests are skipped with a reason.


## P6-T08 QA signal wait with a timeout

- **Components:** `await_qa` in [`flow/workflow.py`](../../packages/flow/src/flow/workflow.py) replaces the T03 stub. In `awaiting-qa` the workflow calls `DBOS.recv("qa", timeout_seconds=...)`: an `approve` message moves it to `done`, `reject` to `rejected`, and no message in time to `timed-out`, all through `next_state`. DBOS stores the deadline, so a restart continues the same wait. [`flow/qa.py`](../../packages/flow/src/flow/qa.py) is the sending side: `send_qa_signal(ticket_id, decision, source, source_id, by)` validates, builds the key with `qa_signal_key` and calls `DBOS.send(workflow_id, msg, topic="qa", idempotency_key=key)`. T09 (MRTR) and T10 (review comment) both call it.
- **Idempotency:** DBOS stores a keyed message once (`message_uuid` unique, insert does nothing on conflict), so a redelivered signal changes nothing; the test sends one key three times, plus once after the run, and finds one row in `dbos.notifications`. A signal with another key after the state left `awaiting-qa` is stored but never read (test: reject after done leaves `done`).
- **Terminal effects (new `GitHubClient.ready_pr` / `close_pr`, fakes in `flow/fakes.py`):** `finish_step` runs `ready-pr` for `done`, `close-pr` for `rejected`, nothing for `timed-out` (PR stays open and draft) and `failed`, then the comment and label with the T02 keys. Both PR effects are keyed by the stable branch and skip when already done. A real client (T04 or later) must implement both methods.
- **Timeout config:** env `ARGUS_FLOW_QA_TIMEOUT_SECONDS` read by `FlowSettings.from_env`, default 60 s so tests and local runs end quickly; `launch` copies it into `Deps.qa_timeout_seconds` unless a test set its own. A deploy must set it (T12), otherwise every ticket times out after 60 s.
- **Links:** `open_pr_step` -> `awaiting-qa` -> `recv` <- `send_qa_signal` <- (T10 webhook handler, T09 MCP tool). The T03 tests now send an approval before expecting `done`.
- **Files:** `packages/flow/src/flow/qa.py`, `workflow.py`, `config.py`, `dbos_runtime.py`, `fakes.py`; `packages/flow/tests/test_workflow.py` (needs Postgres), `test_config.py`.
- **Proof:** with a Postgres and `ARGUS_FLOW_DATABASE_URL` set, `uv run --all-packages python -m pytest packages/flow/tests -q` (170 passed; without the variable the 14 workflow tests are skipped).

## P6-T10 Review-comment fallback for QA approval

- **Components:** [`flow/review_comment.py`](../../packages/flow/src/flow/review_comment.py), a pure parser `parse_review_event(event, payload, reviewers)` and the sender `send_review_signal`. The webhook ([`flow/webhook.py`](../../packages/flow/src/flow/webhook.py), `create_app(..., qa_send=...)`) calls the parser on `pull_request_review` and `pull_request_review_comment` events after the HMAC check. A hit is answered 202 `qa-signal` and `qa_send` runs after the response; nothing is enqueued and nothing is read from GitHub. A miss falls through to the T06 hint path unchanged.
- **Rules (all in the parser, a failed rule is a quiet no-op):** new comment only (`submitted` / `created`); commenter login in `ARGUS_FLOW_QA_REVIEWERS` (unset allows nobody); the PR title is `Argus fix for <ticket_id>` and its head branch is `branch_name(<ticket_id>)`; exactly one of `/argus approve` or `/argus reject` at the start of a line.
- **Same signal as MRTR:** it ends in `send_qa_signal(ticket, decision, "review-comment", "<kind>-<github id>")` from T08, so the idempotency key is `qa_signal_key(...)` and a redelivery is one message. No `mcp` import on this path (a test starts a clean interpreter and checks).
- **Not handled:** `issue_comment` (PR conversation tab), see the `ponytail:` note in the module.
- **Files:** `packages/flow/src/flow/review_comment.py`, `webhook.py`; `packages/flow/tests/test_review_comment.py` (fixture payloads, no Postgres), `test_workflow.py` (end to end through the webhook against Postgres).

## P6-T07 Reconciliation poller

- **Components:** `flow/reconcile.py` and `flow/github_read.py`. `HttpGitHubReader` (GET only, `httpx`, injectable transport, token from `GITHUB_TOKEN`) reads the issue, the PR on the stable branch, the branch ref, the `workflow_dispatch` runs and the comment markers of a ticket into a `GitHubState`. `derive_state` is a pure function from that onto the T02 `State`s (the "GitHub shows" column of [`flow/states.py`](../../packages/flow/src/flow/states.py)). `Reconciler.reconcile(ticket_id)` reads, derives, asks the workflow store (`DbosLookup`), and starts the workflow through the shared `Enqueuer` only when none exists and the state is not an end state; otherwise it reports the state to resume at. A GitHub or database error raises before anything is enqueued. `poll_once()` lists open issues (bounded page size and page count from env) and reconciles each; `poll_forever` is the loop the service runs later (not deployed).
- **Links:** poller -> `GitHubReader` -> GitHub (read only); poller -> `Enqueuer` ([`flow/enqueue.py`](../../packages/flow/src/flow/enqueue.py)) -> `DbosEnqueuer` -> `SetWorkflowID(ticket_id)`, the same call as the webhook ([`flow/webhook.py`](../../packages/flow/src/flow/webhook.py)), so a hint and a poll meet on one workflow; a workflow started from GitHub's state finds the runs, branch and PR through the T03 idempotency keys and opens no second PR. The poller writes nothing to GitHub.
- **Poll defaults** (30 per page, 3 pages, 300 s, minimum 60 s) are a choice for ADR-021/022 to confirm; no cost is claimed (T13, T14 measure). Details, the state table and two findings (PR events carry the PR number as ticket id; run matching depends on T04's run-name) are in [docs/notes/p6-t07.md](../notes/p6-t07.md).

## P6-T04 Dispatch agent jobs to GitHub Actions

- **Components:** `ActionsRunner` in [`flow/actions.py`](../../packages/flow/src/flow/actions.py), the real `Runner` for repro, fix and verify (one instance per step). It uses GitHub's REST API through an injectable `httpx.Client`. `run(ticket_id, run_key, upstream)` finds a dispatched run whose title is `run_key` and waits for it; only if none exists does it send `workflow_dispatch` (inputs `ticket_id`, `step`, `run_key`, `upstream`) and wait for the run to be listed. It polls until completed (bounded), downloads the artifact `argus-result` (`result.json`, `patch.diff`, `trajectory.jsonl`) and returns an `Outcome`. The patch and trajectory stay in `runner.artifacts[run_key]`.
- **Job:** [`agent-job.yml`](../../.github/workflows/agent-job.yml), `workflow_dispatch` only, `run-name: ${{ inputs.run_key }}`, a concurrency group on the key (one running, one pending), read-only `contents`, the model key as the secret reference `ARGUS_MODEL_API_KEY`, inputs passed to scripts only through env. It uploads one artifact and writes a failure `result.json` if the step wrote none.
- **Token:** env `GITHUB_DISPATCH_TOKEN` (fine-grained, Actions read/write on one repository). Sent only in the API `Authorization` header; scrubbed from error texts; a transport error is reported by class name only; httpx drops the header on the artifact download's redirect. Tests assert none of this leaks.
- **Links:** T03 `Deps(repro, fix, verify, github)` takes three `ActionsRunner`s; the run key is `flow.states.effect_key(..., "dispatch-<step>")` and the find-before-start rule is the `dispatch` row of `states.EFFECTS`; T07's poller reads the same run titles; T19 kills the process between dispatch and step result and expects one run.

## P6-T11 Neon config, TLS and reconnect after suspend

- **Components:** [`flow/db_wake.py`](../../packages/flow/src/flow/db_wake.py), `wait_for_database(url)`: connect and `select 1`, retried with exponential backoff (1, 2, 4, 8, 15 s), at most 6 attempts, 5 s connect timeout each; raises `DatabaseUnavailable` and logs only the exception class, never the URL. `launch()` calls it before DBOS starts and `DbosEnqueuer.enqueue` before each hand-over to DBOS ([`flow/dbos_runtime.py`](../../packages/flow/src/flow/dbos_runtime.py)). `require_tls` in [`flow/config.py`](../../packages/flow/src/flow/config.py) makes `FlowSettings.from_env` refuse a non-local database URL without `sslmode=require` (or `verify-ca`, `verify-full`).
- **What DBOS 3.4.0 already does, and so was not rebuilt:** `pool_pre_ping=True` on its engine, and `db_retry` around every system-database operation (step results, `recv`, enqueue): exponential backoff, 1 to 60 s, no deadline. Launch has no retry (fails after one 10 s connect), and the unbounded retry is why the enqueue path probes first. Read from the installed source; details in [docs/notes/p6-t11.md](../notes/p6-t11.md).
- **Links:** webhook ([`flow/webhook.py`](../../packages/flow/src/flow/webhook.py)) and poller (T07) -> `DbosEnqueuer.enqueue` -> `wait_for_database` -> DBOS. Config choices from T03 (`use_listen_notify` off, pinned version and executor id, no conductor key) are now also asserted with the documented Render variables set. Neon endpoint choice (direct, not pooled) and the owner steps for Neon and Render are in the note. T24 builds on the tests added here.
- **Seen locally, not on Neon:** TLS to a local Postgres with a self-signed certificate (all DBOS connections `ssl = true`, TLSv1.3); all sessions killed with `pg_terminate_backend` then the next run finishes; container stopped and started: bounded failure, then reconnect; `launch()` against a stopped server waits and starts. A real Neon suspend was not run.
- **Files:** `packages/flow/src/flow/db_wake.py`, `config.py`, `dbos_runtime.py`; `packages/flow/tests/test_db_wake.py`, `test_config.py`, `test_neon_suspend.py`, `test_launch_wake.py`, `suspend_support.py`; `docs/notes/p6-t11.md`. No change to `pyproject.toml` or `uv.lock`.

## P6-T24 Break it: suspend Neon mid-run

- **Components:** no new component. The test drives the T03 workflow and the T11 reconnect pieces together: the database is taken away inside `fix_step`, after the runner's effect and before DBOS stores the step result. Three cases: all sessions killed (`pg_terminate_backend`); the container stopped and started (DBOS's own `db_retry` blocks on the result write, then continues); a webhook that arrives during the outage (the bounded enqueue in `DbosEnqueuer` gives up, the delivery id is forgotten, the redelivery starts the workflow). Fake call counts show each runner and each GitHub effect happened once.

## P6 GitHub write client

- **Components:** [`flow/github_write.py`](../../packages/flow/src/flow/github_write.py), `HttpGitHubClient`, the real `GitHubClient` (the Protocol in `flow/workflow.py`), and [`flow/diff_apply.py`](../../packages/flow/src/flow/diff_apply.py), an in-memory unified-diff applier. `flow.service.start_engine` now builds `HttpGitHubClient.from_env(cfg.repo)`; `UnwiredGitHub` is deleted. New variable `GITHUB_WRITE_TOKEN` (`sync: false` in `render.yaml`, required by `load_config`): the dispatch token is Actions-only and the poller token is read-only on purpose, so neither can write.
- **Every call finds before it acts** (the T02 effect table): `push_branch` reads the branch ref and stops when the head commit carries the trailer `Argus-Key: <key>`, else applies the diff to the files at the base (branch head, or the default branch when the branch is missing) and creates tree, commit and ref through the git data API (ref created or fast-forwarded, `force: false`). `find_pr` reads `GET /pulls?head=<owner>:<branch>&state=all`, so a closed PR is found too. `create_draft_pr` posts `draft: true`; on a 422 it looks the PR up again and returns it, and raises only if there is none. A lookup error raises `GitHubWriteError`, so `find_or_create_pr` creates nothing and the existing PR is untouched. `ready_pr` uses the GraphQL mutation `markPullRequestReadyForReview` (REST cannot un-draft) and skips a PR that is not a draft; `close_pr` skips a closed one. `post_comment` lists the issue comments (10 pages of 100) and skips when the hidden marker `flow.states.comment_marker(key)` is there. `set_label` adds `argus:<state>` unless present, then removes other `argus:*` labels, ignoring 404. No text the client sends carries a closing keyword (`closes #N`), checked on every request body in the tests.
- **Token:** read from the environment, sent only as the `Authorization` header, absent from `repr`, from `GitHubWriteError` texts (method, path, status and GitHub's message with the token replaced; a transport error is its class name only) and from logs.
- **Ceilings (`ponytail:` comments in the files):** the patch must be a `git diff` of UTF-8 text files with `a/` `b/` prefixes; binary files, renames and copies are refused with a reason, context must match exactly (no fuzz), so a patch made on a `main` that has since moved can fail and the ticket ends `failed`. A repeat push recognises only a head commit that carries the key. Comments and labels are read from the first 10 pages of 100. Commits are authored by the token's user.
- **Seen:** `packages/flow/tests/test_github_write.py` (repeat of every method changes nothing; the 422 race with a stale lookup; 422 with nothing to find; a 500 lookup; the token absent from exceptions, reprs and logs), `test_diff_apply.py` (including a round trip against real `git diff` output), `test_github_write_workflow.py` (the whole `ticket_workflow` on a local Postgres with this client over the fake GitHub: approve ends `done` with a ready PR, reject closes it, a failing lookup ends `failed` with no PR created).
