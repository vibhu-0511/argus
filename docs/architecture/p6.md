# P6 architecture

Source: `phases/P06-argus-flow.md`. P6 runs the ticket-to-fix pipeline as a durable workflow (DBOS), reached by a webhook that is only a hint, repaired by a reconciliation poller, executed on GitHub Actions, with a human QA signal wait. Deployed on Render free with Neon free Postgres. This file grows by one section per task. After each wave the orchestrating session folds the sections into the diagram in `overview.md`.

P6 was started before P5.5 and before P5 finished, on the owner's choice; see `docs/notes/p6-waves.md`.

## P6-T05 Webhook endpoint with HMAC verification

- **Component:** `POST /webhook` in a FastAPI app (`create_app()`), the entry point GitHub calls. It checks `X-Hub-Signature-256` (HMAC-SHA256 over the raw body) before anything else is read from the body.
- **Secret:** the environment variable `GITHUB_WEBHOOK_SECRET`, read on each request; never stored in a file or logged. Compare is `hmac.compare_digest`. Valid -> 202; invalid, missing or malformed header -> 401; no secret or an empty one -> 401 for every request (fail closed).
- **Links:** GitHub (sender) -> this endpoint. T06 adds the hint handling behind the same check; T12 deploys the app on Render.
- **Files:** `packages/flow/src/flow/webhook.py`, `packages/flow/tests/test_webhook.py`.
- **Proof:** `uv run pytest packages/flow/tests -q`

## P6-T06 Webhook as a hint: enqueue and return 202

- **Components:** the `/webhook` handler (after the T05 signature check) reads `X-GitHub-Event` and `X-GitHub-Delivery`, derives the ticket id `owner/repo#number` from the payload's `issue` or `pull_request`, schedules `enqueue_reconcile(ticket_id)` as a background task and returns 202. It reads nothing from GitHub. An event with no issue or PR number (ping, push, workflow_run) is acknowledged as `ignored` and not enqueued; the poller covers it. A signed body that is not JSON gets 400.
- **New seam:** `Enqueuer` Protocol in `flow/enqueue.py`, with `FakeEnqueuer` (tests) and `HintDedup` (bounded in-memory set of delivery ids, per process). The real DBOS implementation arrives in T03 and starts the workflow under `SetWorkflowID(ticket_id)`; T07's poller makes the same call, so webhook and poller share one workflow id per ticket. The delivery id is never a workflow key. A failed enqueue forgets the delivery id so GitHub's redelivery is not dropped.
- **Links:** T05 (signature check) -> handler -> `Enqueuer` -> T03 workflow; T07 poller -> same `Enqueuer`.
- **Files:** `packages/flow/src/flow/enqueue.py`, `packages/flow/src/flow/webhook.py`, `packages/flow/tests/test_webhook.py`.
- **Measured handler time:** a test drives the app as an ASGI server with a fake enqueue that sleeps 2 s. The response was fully sent after 0.8 to 1.8 ms (4 runs on this machine, in-process, no real network); the app returned after about 2.0 s because the enqueue ran after the response. This is the handler only, not a Render cold start (that is T13).
- **Proof:** `uv run pytest packages/flow/tests -q -s` (the `-s` shows the timing line)

## P6-T22 Break it: duplicate webhook delivery

- **Components:** no new component. The test exercises `HintDedup` and the ticket-id workflow key from T06: a repeated delivery id is answered 202 `duplicate` and not enqueued; with the record off, lost or evicted, the repeat is enqueued but lands on the same workflow id.
- **Links:** `flow.webhook` -> `HintDedup` -> `Enqueuer` (fake now, DBOS `SetWorkflowID(ticket_id)` in T03).
- **Files:** `packages/flow/tests/test_duplicate_delivery.py`, `docs/notes/p6-t22-break-it.md`.
- **Proof:** `uv run pytest packages/flow/tests/test_duplicate_delivery.py -q`
