Argus · one ticket in production

A labelled GitHub issue becomes one durable workflow. The state machine calls one specialist per state, checkpoints the result, and opens a single pull request. Specialists return a result and stop. They do not message each other.

Source of truthTenant GitHub repoIssue, pull request, and Actions run. The agent job executes here, in the tenant's reusable workflow.
Control planeFastAPI + DBOS on RenderDurable steps in Neon Postgres. Accepts webhooks, dispatches work, waits for QA.
ExecutionGitHub ActionsRepro, locate, fix, and verify run in a worktree and a Docker sandbox with no network.
ModelsRouter + quota ledgerCheap tier for repro and locate. Strong tier for the fix. Local cross-family judge after the checks.

Pay button is clipped on a phone. On /cart at 375px the “Pay now” button runs off the right edge. Expected: the full button sits inside the viewport. This page follows that ticket. Amounts such as tokens and latency stay blank until a real run writes them.

Who orchestrates

DBOS is the orchestrator. A planner with subagents stays off unless the P8 ablation wins on both resolve rate and tokens per bug.

  1. Read GitHub, then advance one state.
  2. Dispatch that state to Actions.
  3. Store the step result before the next transition.
    GitHub is the record

    The webhook asks the service to look. The reconciliation poller rebuilds state from the issue, the pull request, and the Actions run.

    One effect, safe to retry

    Opening a pull request is find-or-create, keyed by the ticket. A crash after the PR exists and before the checkpoint still leaves one PR.

    Checks decide

    Pixel diff, overflow, axe, and console run in that order and stop at the first hard failure. The vision judge writes an intent note after a full pass.

    Code stays in the tenant repo

    The control plane mints a short-lived installation token for that repo only. The sandbox has no network. Free-tier prompts see public code only.
